# Changelog

## Unpublished

### 🛠 Breaking changes

- **The v1 surface is narrowed: five commands are deferred and two are renamed.** None of them ever shipped — every entry below is from this same unpublished cycle — so this is what the first release will and will not have, rather than a removal from anything anybody has.

  **Deferred**, code kept as reference under `packages/exagent/src/deferred/`, imported by nothing:

  - `exagent dev:wait` — `exagent smoke` asks every question it asked and three more, in one command. Its jobs map onto `smoke` (the gate), `runtime:errors --fail-on-error` (app health over a window) and `dev --detach --wait-ready` (readiness at start), and every suggestion this CLI prints was rewritten to name those. The library internals stay, so nothing about the bundle check or the readiness wait changed.
  - The **checkpoint system, whole** — the `checkpoint` group, the automatic snapshots `install`, `agents:setup` and a prebuilding `dev` plan took, the `--no-checkpoint` flags, and `EXAGENT_NO_CHECKPOINT`. Agents manage git themselves, and a second snapshot mechanism beside git is a second thing to reason about rather than a safety net. `install --json` loses its `checkpoint` key.
  - `exagent build:wait` — it will return as `exagent build --wait`, on a build verb this CLI owns, with the same flag waiting on a local build and on an EAS one. A caller who wants to wait has already run a build command; carrying an id between two commands is the shape that was wrong.
  - `exagent runtime:network` — React Native ships the debugger's Network domain behind an unstable flag and Expo Go for Android implements none of it, so on the runtime an agent is most likely to meet, the command's usual answer was an explanation of why it could not answer.
  - `exagent doctor:fix` — `doctor` and `doctor:check` are unchanged and are the v1 answer. What the fix half deletes is caches and build state, and an agent deletes those today with one line of shell; the tier table and its safety rules are worth shipping once the surface they sit in is settled.

  **Renamed** into a new `inspect` group, which is named after what the caller is doing rather than after another CLI's verb — same flags, same output:

  - `exagent build:explain` is **`exagent inspect:build-log`**.
  - `exagent config:effective` is **`exagent inspect:config-plugins`**. The old name was reachable by its colon form only, because `exagent config` is `expo config`; the new one takes the space form too.

  `exagent build` is now a name this CLI does not have, and answers with `npx eas build` and a pointer to `inspect:build-log`. And three commands are marked **`[experimental]`** in `--help` — `inspect:build-log`, `inspect:config-plugins` and `smoke` — with one footnote per section saying they may change or vanish. The mark is per command and never per group: `inspect` is a group a stable action can join. ([#49229](https://github.com/expo/expo/pull/49229) by [@expo-tuft[bot]](https://github.com/apps/expo-tuft))

- The plan-first engine is `exagent dev`, and `exagent start` is `expo start`. A command that shares its name with an `expo` command behaves like that command, so `exagent start` probes nothing and plans nothing: it forwards every argument it does not own to `expo start` untouched and syncs agent skills once the dev server is up, which is what `start --passthrough` did. Everything the plan engine owns moved to the new `exagent dev` verb with the same surface — `--plan`, `--yes`, `--json`, `--ios`/`--android`/`--web`, `--no-followups`, `--no-checkpoint`, `--no-agent-skills` — and the flags `--smart` and `--passthrough` are gone from both commands, because neither has a mode to pick any more. A terminal facing a `dev` plan that installs, prebuilds or builds is asked `Run this plan?` once before the first step runs; declining runs nothing and exits 0, `--yes` answers it up front, and a run that cannot be asked (an agent, CI, `--json`) proceeds without a prompt. The follow-up ids of the plan engine changed with it: `start-smart` is now `dev` and `start-plan` is now `dev-plan`, and the `cli:followups` event of a `dev` run names `dev` as its command. ([#49229](https://github.com/expo/expo/pull/49229) by [@expo-tuft[bot]](https://github.com/apps/expo-tuft))
- A capability with several actions is now one colon group, the way `eas-cli` spells its own commands: `runtime eval|errors|network` is `runtime:eval|runtime:errors|runtime:network`, the `skills` actions are `skills:sync|skills:list|skills:show|skills:clean`, and `exagent setup` is `exagent agents:setup`. The checkpoint guardrail is one group too: `exagent checkpoint` still takes the snapshot, `undo --list` is `exagent checkpoint:list`, and the top-level `exagent undo` is **removed** in favor of `exagent checkpoint:undo` (`--id` unchanged, `--list` gone with the command it was on). The colon is canonical and the space form resolves to the same command, so `exagent skills list` keeps working, and a bare group prints its actions unless one of them is the obvious default (`exagent checkpoint` snapshots, `exagent skills` syncs). An action a group does not have fails with `UNKNOWN_ACTION` and the listing of the ones it does, and is never forwarded to `expo`. `exagent --help` now groups the commands by the job they do — Develop, Create, Deployment, Debug a running app, Agent setup, Checkpoints, Expo CLI — instead of listing them alphabetically. Two names moved with the surface: the follow-up id `setup` is now `agents-setup`, and the JSONL event `setup:completed` is now `agents:setup_completed`. ([#49229](https://github.com/expo/expo/pull/49229) by [@expo-tuft[bot]](https://github.com/apps/expo-tuft))
- `exagent context` is **removed**, merged into `exagent status`. `status --json` now carries the raw project probe verbatim under a new top-level `probe` key — the exact object `context --json` printed, minus its own `followups` — alongside the sections it already had, so the Expo Go reasons the `expoGo` section only counts and the fingerprint error the `freshness` section abbreviates are readable in the same report. The two commands shared one probe and differed only in how much of it they printed, and `status` reads that probe anyway, so the brief costs nothing extra. The `install-dev-client` follow-up moved from `context` to `status`, and the `project-context` follow-up of `status` is gone with the command it named; the `project-context` follow-up of a `dev` plan now points at `npx exagent status --json`. ([#49229](https://github.com/expo/expo/pull/49229) by [@expo-tuft[bot]](https://github.com/apps/expo-tuft))
- The `expo` commands `exagent` does not wrap are forwarded to the project's `expo` CLI as a subprocess, so `exagent prebuild --clean` runs `expo prebuild --clean` with the stdio inherited and the exit code forwarded verbatim. Nothing is added to a forwarded run — no probe, no skill sync, no follow-ups — and each forward emits one `cli:expo_passthrough` event naming the command and its arguments. The forwarded set is **fixed**, taken from the command map of `@expo/cli` minus the commands `exagent` wraps: `run`, `run:ios`, `run:android`, `prebuild`, `config`, `export`, `export:web`, `export:embed`, `serve`, `customize`, `lint`, `login`, `logout`, `register`, `whoami`. `expo add` is `expo install` under another name, so `exagent add` is not forwarded either: it is an alias of the `exagent install` wrapper, and gets the same skill sync, impact report and checkpoint. It is not an open-ended fallback: a name in neither `exagent`'s own surface nor that set fails with `UNKNOWN_COMMAND` naming where commands come from, because an unrecognized name is a typo far more often than it is a new `expo` command, and forwarding it made the typo the `expo` CLI's problem to report. ([#49229](https://github.com/expo/expo/pull/49229) by [@expo-tuft[bot]](https://github.com/apps/expo-tuft))
- `exagent <group> <options>` with no action now **fails** instead of printing the group's actions and exiting 0. `exagent runtime --json` used to answer with the listing and a success code, which a driving agent reads as "that worked" before waiting for output that is never coming; it now prints the listing, then `UNKNOWN_ACTION` naming the actions those options could have belonged to, `Try: npx exagent runtime --help`, and exits 1. A bare group is unchanged — `exagent runtime` still lists its actions and exits 0 — as is `<group> --help`, and a group with a default action still gets its options: `exagent checkpoint --label x` snapshots. Two conventions ride with it (`llp/0010`): the exit codes of every command now come from one table — 0 success, 1 the tool did not work, 7 a person must finish the step, 20/21/22 the operation failed, was canceled, or timed out — and a command group named after a forwarded `expo` command keeps the forwarded behaviour for its bare form and owns only its colon forms, so a future `config:*` group cannot take `exagent config` away from `expo config`. A forwarded subprocess's code is still handed back verbatim; the one shipped command re-coded since is the `deploy` auth failure, below. ([#49229](https://github.com/expo/expo/pull/49229) by [@expo-tuft[bot]](https://github.com/apps/expo-tuft))
- `exagent dev` is a command **group** now, so that `dev:wait` could join it, and `exagent dev --help` prints the group's actions instead of the plan engine's options. Running the command is unchanged: `dev` declares `run` as its default action, so `exagent dev`, `exagent dev --plan --ios` and every other invocation still run the plan engine with every option they were given. Only help moved one hop — the `--plan`/`--yes`/`--json` block is `exagent dev:run --help` — which is what `<group> --help` has always meant for `checkpoint` and `skills` (`llp/0010` §Registry rules). ([#49229](https://github.com/expo/expo/pull/49229) by [@expo-tuft[bot]](https://github.com/apps/expo-tuft))

- `install --json`'s `check` key is now a report of this CLI's own rather than the Expo CLI's payload passed through. `exagent install --check --json <package>` on a package the project does not have exited **1** with a success-shaped object — `installed: false`, `check: null`, the code buried in the body — and **zero bytes on stderr**: the whole verdict was in the exit code, and `--check` is the natural first move for an agent deciding whether to install something. Two things were losing it. The wrapper suppressed the Expo CLI's output for every `--check` run, which is right when the CLI gets far enough to print its report and wrong when it throws `PACKAGE_NOT_FOUND` before then; and `check: null` meant both "no payload" and "this was not a `--check` run". `check` now carries `ok` (the verdict, with no prose to parse), `report` (the Expo CLI's `{dependencies, upToDate}`, verbatim, or null), `output` (what it printed when it produced no report — also echoed to stderr now), and `notes`. The notes are the third fix: the message the Expo CLI prints says the package "is added as a dependency in your project's package.json", and for the package this was reported against it was not there at all, so `exagent` reads the manifest itself and says which of the three states the project is actually in. A human `--check` run gets the same correction as a last line under the Expo CLI's own output. ([#49229](https://github.com/expo/expo/pull/49229) by [@expo-tuft[bot]](https://github.com/apps/expo-tuft))

- `config:effective`'s `autolinkedModules` is now **`expoAutolinkedModules`**, and it carries a `expoAutolinkedModulesNote` saying what it does not cover. The list has always been Expo-module autolinking only — packages that ship an `expo-module.config.json` — which is a defensible scope that the name did not state, so `exagent install @react-native-async-storage/async-storage --json` classified the package `native-module` and `exagent config:effective --json` then left it out, and an agent asking "is my native dependency linked?" was told no by a list that had never been asked the question. A React Native community module is linked by React Native's own autolinking and still never appears there; the note names `install --json` as where to read about those. The human report prints `Autolinked 21 Expo modules (React Native community modules link separately)` and the `cli:config_effective` event field `autolinkedModuleCount` is now `expoAutolinkedModuleCount`. ([#49229](https://github.com/expo/expo/pull/49229) by [@expo-tuft[bot]](https://github.com/apps/expo-tuft))

- A command that stops on a step only a person can complete now exits **7** instead of 1, and ends with a three-line handoff naming what its user has to do. It reaches two shipped failures of `exagent deploy`: the launch CLI refusing for lack of a login (`LAUNCH_NOT_AUTHENTICATED`) and an `eas deploy` that stopped on an account or a prompt (`EAS_DEPLOY_FAILED`), plus an `expo export` that stopped on a prompt (`EXPORT_FAILED`). The codes are unchanged; only the exit code and the last lines of output are. Anything that treated a non-zero exit from those commands as "the call was wrong" now has a third answer to read: 0 the tool worked, 1 the tool did not work, 7 the tool worked and is waiting on a human. ([#49229](https://github.com/expo/expo/pull/49229) by [@expo-tuft[bot]](https://github.com/apps/expo-tuft))

### 🎉 New features

- **`exagent runtime:tree`, `runtime:tap` and `runtime:type` drive the running app by `testID`** — marked **`[experimental]`**. `runtime:tree` lists what is on the screen, `runtime:tap <testID>` presses an element, and `runtime:type "<text>" --testID <id>` puts text into an input, with `--submit` calling `onSubmitEditing` after it. Between `navigate`, which opens a route, and `runtime:eval`, which reads state, nothing in this CLI pressed a button; these are that. They were gated on a live spike because every claim about React's internals behind them was inferred, and the spike came back GO with three of its five findings changing the command shapes (`llp/0014`, `llp/0018`).

  They walk React's own component tree through the DevTools hook a development bundle installs, and call the `onPress` or `onChangeText` **the app wrote** — so this calls props, it does not touch the screen. Three rules make that work on a real screen. A `testID` written once in JSX lands on every fiber that forwards props down to a host view — 17 fibers for 4 elements on the screen this was measured against — so a match is an **element**, a fiber no ancestor of which carries the same testID, and `--index` is needed only when two real elements share one. Inside that element the **shallowest** handler wins: `react-native-gesture-handler`'s `RectButton` puts `onPress` on six fibers of one group and only the outermost is the app's function, while the deepest is the library's internal press handler, which expects the library's event. And when the handler comes from an **ancestor** of the element you named — tapping a `Text` inside a card — the report says `handlerOutsideMatch: true` rather than firing it silently.

  An app keeps the screens you are not looking at **mounted**, so the whole tree describes three screens at once. All three commands default to the screen React Navigation reports as focused, and name it in the report; where focus cannot be read they report everything with `focusedScreen: null`, which is honest rather than an error, and `--all-screens` asks for the whole tree on purpose. `runtime:tree` also defaults to what you can act on — nodes with a handler or a testID — because that stays a fixed size as the app grows, where the full projection went from 12 KB to 241 KB with 300 more list rows; `--all` is the full projection and `--max-nodes` bounds either and says `truncated`. There is no `--depth`: fiber depth on a real screen runs to 152 and every visible element sits between 128 and 152.

  **A disabled element is refused, not tapped.** React Native disables a press at the responder level, which this never goes through, so `onPress` is still on the props of a `disabled` button and calling it would report a pass for something a user cannot do — the one correctness bug the spike found in the mechanism. That is exit **20**, and `--force` overrides it and says so in the report; the same holds for `editable={false}` on an input. The other honest limits are in each command's `--help` rather than in a footnote: no press timing, no responder chain, no gesture recognition, a synthetic event whose coordinates are zero, an invisible button indistinguishable from a visible one, nothing at all on Expo Go for Android, and a production bundle refused with `RUNTIME_TREE_UNSUPPORTED` rather than answered with an empty screen.

  `runtime:tap --verify` is the only proof on offer: it walks the tree again a second after the tap and reports what appeared, vanished or changed text. `changed: false` is printed as "the handler ran and nothing in the component tree moved" — a network call, a navigation this walk cannot see, or nothing at all — and never as "the tap did nothing". Without it, the only claim made is that the handler was called. Exit codes follow the table: **0** the call was made, **20** nothing was called (no element carries that testID, several do, it is disabled, it has no handler) or the app's own handler threw, **1** the app could not be read at all. Every string that came out of the app is fenced in untrusted-content markers, and `--json` prints one object with a key set that does not vary between the outcomes. Three new JSONL events ride with them: `cli:runtime_tree`, `cli:runtime_tap` and `cli:runtime_type`. ([#49229](https://github.com/expo/expo/pull/49229) by [@expo-tuft[bot]](https://github.com/apps/expo-tuft))

- **`exagent status` says what a change costs, on every run.** A new `impact` line reports the class of everything that has changed since the last build this CLI made — `js-only`, `dev-client-compatible` or `needs-native-build` — with the one sentence that says what carried it, and `freshness.platforms[].impact` carries the same in `--json`. `stale` was a fact and this is what to do about it, which used to be a second command away. It costs nothing: both fingerprints are already in memory (the probe computed the working tree's sources to get its hash, and `.expo/exagent-last-build.json` has stored the last build's since the v2 record), and the diff between them now runs **in process** instead of spawning `fingerprint:diff` over two temp files. Measured on a real 210-source project: 1.58 s before the line existed, 1.57 s after. The local diff is a port, pinned item-for-item against a recorded pair of real fingerprints and the real CLI's answer for them — which is what catches the rule a reimplementation gets wrong, that a package's identity is `name@version` so a version bump is a removal plus an addition, never a change. The third class needs one more thing the fingerprint cannot see: a `metro.config.js` or `babel.config.js` edit leaves the native surface untouched and still needs Metro restarted, so when the fingerprint says nothing moved, `git status --porcelain` (20–240 ms live, behind a deadline) splits `js-only` from `dev-client-compatible`; a project outside git simply keeps the fingerprint's answer. Where nothing could be classified — no recorded build, or a v1 record holding only a hash — the class is **null** and the line is left out entirely, because the `freshness` line above has already said why. ([#49229](https://github.com/expo/expo/pull/49229) by [@expo-tuft[bot]](https://github.com/apps/expo-tuft))

- **`exagent status --explain` is the deep dive**, and it is the one flag that means "you may pay". Three things join the report and only two of them cost anything: the per-source change list is free (the headline already diffed locally) and is withheld by default because a headline with fifty rows attached is not a headline; the OTA verdict spawns `expo config --json --type public` to resolve the `runtimeVersion` policy; and the EAS build lookup below makes its network call. Live on the same project, 1.57 s becomes 3.29 s. `--explain --build <id>` compares against a specific EAS build's own fingerprint instead of the local record — server ground truth, no local record needed — and says so on the line (`impact  vs EAS build 21d7d434-… · needs-native-build`); the `fresh`/`stale` states are left alone, because "is the app I built here still current" and "does this differ from that cloud build" are two questions and one of them silently changing meaning would be worse than reporting both. `--build` requires `--explain` and says so rather than implying it, because it is the flag that spends the round trip. ([#49229](https://github.com/expo/expo/pull/49229) by [@expo-tuft[bot]](https://github.com/apps/expo-tuft))

- **`exagent status --assert <class>` is the gate, and `exagent impact` is removed.** The assertion exits **20** when the change costs more than the class named, **22** when no class could be established, and **0** otherwise — and prints the whole report either way, because the exit code is the answer and the payload is why. Without the flag the command still always exits 0. The exit-0 contract is not broken by this: it is about what a *report* does, and `--assert` is a caller asking for a verdict instead, which is the shape `runtime:errors --fail-on-error` has had all along. `22` is the code that keeps the gate honest — `status` refuses to name a class it did not establish, and a gate that returned 0 because nothing was measured would not be a gate; the two failures need different fixes, so they get different codes. A platform with **no recorded build** is skipped rather than dragging the answer to `22`, because there is no installed app there for the change to break; a platform that *was* built and cannot be measured is not. With `--assert` and `--build` on `status`, nothing was left of `exagent impact` but two flags that changed only its caveats, so the command is **gone** and its modules are the engine under `status`. Nothing it could do went with it: `--base`/`--head` never worked (it threw `IMPACT_MODE_UNAVAILABLE` on every run), and `--preset`/`--profile` are dropped, having only ever reached the fingerprint run and the caveat list. The follow-up ids `impact-*` are now `change-*` — they name what a change costs, not a command — and `impact-cached-build`/`status-cached-build` are one id, `cached-build`. `cli:status` gains `impact` and `assertion`; `cli:impact` is now `exagent install`'s package classification, which is the only thing still emitting it. ([#49229](https://github.com/expo/expo/pull/49229) by [@expo-tuft[bot]](https://github.com/apps/expo-tuft))

- **`exagent status` says whether EAS already has a build of what is on disk**, on a new `eas build` line and under a `builds` key in `--json`, per platform and in three states: `found`, `none`, or `unknown` with the reason. It is the other half of the freshness question — `freshness` answers "does the app *this machine* built still match", while this answers "has anybody already built exactly this", where the answer is `eas build:download` rather than a fifteen-minute rebuild. The **cached** answer is reported on every run and the **network call rides with `--explain`**, because the two are not the same cost: a lookup measured 1.10–1.33 s live and needs a *second* fingerprint run first (1.24 s), since `status` hashes both platforms together for freshness and an EAS build carries a per-platform hash — `031f6b0c…` and `8ce1acfb…` for the same working tree. No deadline can make that instant, so instead the answer is cached in `.expo/exagent-eas-builds.json` against the project fingerprint `status` computes anyway; that key is *exact* rather than approximate, because the whole-project hash dominates the per-platform ones. Only a hit is cached — a "there is no build" goes stale the moment a queued build finishes. Nothing about this can fail the command: no EAS CLI, no `@expo/fingerprint`, a project with no EAS link, a refused network, an unreadable payload or an expired deadline each cost that one section its answer and nothing else, and a signed-out machine is reported from the `auth` section rather than probed a second time. A `found` platform whose own recorded build is `stale` also gets a `status-cached-build` follow-up, which is `impact`'s `impact-cached-build` rung reached from the other direction. The `cli:status` event gains `easBuilds` and `easBuildsAsked`. ([#49229](https://github.com/expo/expo/pull/49229) by [@expo-tuft[bot]](https://github.com/apps/expo-tuft))

- **`exagent dev` picks where a native build runs, and the plan says which and why.** A build happens in one of two places — `local`, on this machine with Xcode or the Android SDK, or `eas`, in the cloud with an Expo account — and until now every plan was the local one, with a warning printed above it when this machine could not do it. The choice is now made *while the plan is being decided*, so a machine with no Xcode gets `eas build --platform ios --profile development` in the plan's **steps**, followed by `expo start --dev-client`, instead of a `expo prebuild` + `expo run:ios` that would stop at the compiler many minutes later. Nothing is ever swapped mid-run: the selection is visible in `--plan` before anything starts, which is what makes the plan an agent approves the plan that runs (`llp/0008`). Two answers read differently on purpose — a host that **cannot** have the toolchain (iOS on Linux or Windows) is told that no install would change it, and a host that merely **has not installed** it is told how — and a probe that could not run leaves the build here, because a build queue is the wrong place to send somebody over a question nobody could answer. `--eas` and `--local` name the place outright; `--local` on a host that cannot build is honoured, and the plan says out loud that its build step will fail. The EAS route adds `eas build:configure` first when the project has no `eas.json`, has no prebuild step (EAS Build generates the native project itself), and names `npx eas build:run --platform <p> --latest` as the way to install the artifact — installing is guidance rather than a step, because it needs a device the host that sent the build to the cloud may not have. `dev` runs `eas` plan steps through the project's own `eas` CLI, the same process boundary as every other member of the family. `StartPlan.buildLocation` gains a `selection` object (`runsOn`, `source`, `because`, `why`, `doomed`) on the `--json` payload and the `cli:start_plan` event, and `ToolchainProbe` gains `impossible`. ([#49229](https://github.com/expo/expo/pull/49229) by [@expo-tuft[bot]](https://github.com/apps/expo-tuft))

- **A project can tell `exagent` what to prefer**, in `package.json` under `expo.exagent` — beside `expo.install`, `expo.doctor` and `expo.autolinking`, which is where Expo tooling configuration already lives. Two keys: `target` (`expo-go` or `dev-build`), which plans a development build even for a project Expo Go could run; and `buildBackend` (`local` or `eas`), optionally per platform under an `ios` or `android` key. `--go`/`--dev-client` and `--eas`/`--local` are the one-run form of the same two questions, and a flag beats the config, which beats detection. Every decision a preference changed is labelled — in the plan's `Why` list, in `status`, and in `impact`'s follow-ups — so a plan the config moved is never mistaken for one it did not, and a preference that changed nothing says that too. A key or value this version does not know is an **error** naming the keys it does, not a warning: this config exists to change what a build does, and one that was silently dropped leaves you approving a plan you did not ask for. Deliberately not `app.json`: a top-level key there is dropped with a warning by `@expo/config` whenever an `expo` object exists, and a key under `expo.extra` is part of the project **fingerprint**, so a preference about tooling would mark every existing development build stale. ([#49229](https://github.com/expo/expo/pull/49229) by [@expo-tuft[bot]](https://github.com/apps/expo-tuft))

- **`exagent status` reports where the next build would run**, on a new `build` line and under `next.buildLocation` in `--json`: the place, and the one clause that says what chose it. It resolves the plan the way `dev` does — the config, this host, the toolchain probe — so the two commands can never disagree about what happens next, and a `status` on a Linux box no longer names `expo run:ios`. The line is left out entirely when the next plan builds nothing. A config `status` cannot read costs it that line and nothing else: the command still exits 0 with every other fact in the report. ([#49229](https://github.com/expo/expo/pull/49229) by [@expo-tuft[bot]](https://github.com/apps/expo-tuft))

- **The follow-ups know which route the plan took.** A `dev --plan` whose build runs on EAS now leads with `npx eas whoami` — the account that build will be queued under, which is a failure that otherwise arrives after the upload — instead of offering the cloud route the plan already took. `eas-build-instead` survives for the one case that still needs it: a `--local` or a config that asked to build here on a machine that cannot. The `needs-native-build` answer says which of its two routes the plan engine would pick and why, and offers `npx exagent dev --local` as the way past a choice the caller disagrees with. - **`exagent runtime:reload --cloud` now reloads the app on an EAS cloud simulator, and it is proved on the dev server rather than assumed.** It did not before, even with "1 app connected" on the screen, and the reason was one sentence in the code: the broadcast "reaches a cloud session already — a cloud session has to reach that dev server through a tunnel to be running the bundle at all". The tunnel carries the **bundle**, over HTTP; the app holds no client on the dev server's client command socket through it. So the broadcast reached nobody, `auto` fell through to a force-stop, the relaunch was refused, and a billed session was left with nothing running on it.

  `--cloud` now changes the **ladder**, not a fallback. `auto` runs two controller verbs — `open <app-id> --platform ios --relaunch`, then `open <url> --platform ios` — and reaches them even with an app on the dev server's target list, because the rule that protects a connected app ("never force-stop one you can see") protects an alternative a cloud session does not have. There is no `close` anywhere in the path: that is the verb that ended the *controller's* session and is what left the app stranded. The URL is the manifest-derived tunnel URL `navigate --cloud` uses, never the `exp+<slug>://<host>` launcher form, and a dev server the session cannot reach is refused **before** the app is touched, so a bad URL can no longer take the app off the screen. A `DEVICE_IN_USE` refusal is retried once bound to the session the controller names, which never starts a second billed machine.

  The two verbs are two because the documented one-verb form kills the app: cold-launching Expo Go *with* a dev-server URL crashed it on its own updates database — `SQLiteGetResultsError … UNIQUE constraint failed: updates.scope_key, updates.commit_time` — twice out of two on a live session. Restart the shell, then send the link.

  **What proves it.** A cloud simulator's relaunched app re-registers under the *same* debugger page id, so the fresh-target test that proves every other reload cannot prove this one. `runtime:reload` now also watches the dev server's own captured output for a `Bundled` line that was not there before the relaunch, which means something fetched the served bundle again; the two observations share one budget and the first to answer ends both. `verifiedBy` gains `dev-server-bundle`, and `reloaded` is now true only when one of them was observed — so a cloud relaunch nothing confirmed is exit `22` with both observations spelled out, instead of a success taken from a verb that merely accepted its arguments. `--json` grows `commandSocketClients` and `bundlesAfterReload`; the human report prints the command-socket count on its own line, because one number for two different lists is what made "Apps connected 1" sit above a broadcast that reached nobody.

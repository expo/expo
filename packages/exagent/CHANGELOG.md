# Changelog

## Unpublished

### 🛠 Breaking changes

### 🎉 New features

- Initial `exagent` package: `skills` command (sync/list/show/clean) ported from the `@expo/cli` proof-of-concept. ([#49229](https://github.com/expo/expo/pull/49229) by [@expo-tuft[bot]](https://github.com/apps/expo-tuft))
- Add `exagent start --plan` and `exagent start --smart`: decide between `expo start`, `expo prebuild`, and `expo run:*` from the project state, emit the plan with time-class estimates, then optionally run it. ([#49229](https://github.com/expo/expo/pull/49229) by [@expo-tuft[bot]](https://github.com/apps/expo-tuft))
- Add the project-state probe with the Expo Go compatibility check, the `exagent context` command (`--json` for the machine-readable project brief), and the post-install impact report of `exagent install` (`--no-impact` to skip it). ([#49229](https://github.com/expo/expo/pull/49229) by [@expo-tuft[bot]](https://github.com/apps/expo-tuft))
- Add `exagent runtime eval` and `exagent runtime errors`: evaluate JavaScript in the running app and collect its runtime errors over the dev server's debugger connection, with app output fenced in untrusted-content markers and `--json` for the machine-readable shape. ([#49229](https://github.com/expo/expo/pull/49229) by [@expo-tuft[bot]](https://github.com/apps/expo-tuft))
- Add `exagent runtime network`: collect the HTTP requests the running app makes over a time window, one line per request with its status and content type, fenced in untrusted-content markers (`--duration` for the window, `--json` for the machine-readable shape). A request the runtime answered, one it reported as failed, and one it never answered are three separate outcomes, because React Native reports a connection error to JavaScript without sending `Network.loadingFailed`. When the connected runtime does not implement the debugger's Network domain — still an unstable part of React Native — the command reports `NETWORK_DOMAIN_UNAVAILABLE` and points at `exagent runtime errors`, instead of printing an empty list that reads like "the app made no requests". ([#49229](https://github.com/expo/expo/pull/49229) by [@expo-tuft[bot]](https://github.com/apps/expo-tuft))
- Add `exagent status`: a read-only, `git status`-like overview of the project, the Expo Go verdict, the freshness of the last recorded development build per platform, the dev server and the apps connected to it, the linked agent skills, and the command that would get the app onto a device (`--json` for the machine-readable report, `--dev-server-url` to probe another dev server). ([#49229](https://github.com/expo/expo/pull/49229) by [@expo-tuft[bot]](https://github.com/apps/expo-tuft))
- Add `exagent navigate <route>`: open a route as a deep link on the booted simulator or attached device, resolving the URL shape from the app connected to the dev server (`exp://` for Expo Go) and the `scheme` field of the app config (`--scheme` to override). ([#49229](https://github.com/expo/expo/pull/49229) by [@expo-tuft[bot]](https://github.com/apps/expo-tuft))

- Add `exagent setup`: link the agent skills of the installed packages, then create or update one managed block in the project's `AGENTS.md` with the project facts from the probe and the command cheat sheet (`--agent` to pick the agents, `--no-agents-md` and `--no-agent-skills` to skip either half, `--json` for the machine-readable report). Content outside the block markers is preserved byte for byte, and `CLAUDE.md` is never written. ([#49229](https://github.com/expo/expo/pull/49229) by [@expo-tuft[bot]](https://github.com/apps/expo-tuft))

- Add `--json` to `exagent navigate`: print the opened URL, how it was resolved, the target app, the device, the device command and its exit code as one JSON object on stdout. ([#49229](https://github.com/expo/expo/pull/49229) by [@expo-tuft[bot]](https://github.com/apps/expo-tuft))

- Add `exagent new <directory>`: create a project with no TTY attached, by running `create-expo` as a subprocess with every prompt answered (`--name` to set the display name in `app.json`, `--no-install`, `--no-git`, `--json` for the machine-readable report). It initializes a git repository when `create-expo` left none and the project is not already inside one, and forwards the exit code of a failed scaffold. ([#49229](https://github.com/expo/expo/pull/49229) by [@expo-tuft[bot]](https://github.com/apps/expo-tuft))

- Add `exagent deploy`: ship the web app to EAS Hosting (`expo export --platform web`, then `eas deploy --non-interactive`) and the native app through EAS Build (`--platform ios|android`, `--profile`, default `production`), reporting the deployment and build URLs parsed from the EAS output (`--json` for the machine-readable report, `--web`/`--native` to pick the targets, both at once for a cross-platform deploy). With no target flag, a project that depends on `react-native-web` deploys its web app. Native delivery through launch.expo.dev is still pending, so the native target stops at the EAS Build page and says so. Missing prerequisites are reported before anything is spent: `EAS_CLI_MISSING` and `EAS_NOT_CONFIGURED` each carry the one command that fixes them. ([#49229](https://github.com/expo/expo/pull/49229) by [@expo-tuft[bot]](https://github.com/apps/expo-tuft))

- Add `exagent checkpoint` and `exagent undo`: snapshot the project before a change, and put the snapshot back. A checkpoint is written with git plumbing against a temporary index (`git add -A` → `git write-tree` → `git commit-tree`), so it commits nothing onto the user's branch and leaves `HEAD`, the branches, the reflog, and the index untouched; the object ids are recorded in `.expo/exagent-checkpoints.json`, capped at the 20 most recent. `exagent install`, `exagent setup` and a `exagent start --smart` plan that prebuilds each take one before they change anything, best-effort and never able to fail the command (`--no-checkpoint` or `EXAGENT_NO_CHECKPOINT` to skip it). `exagent undo` restores every file of a checkpoint (`--list` for the recorded ones, `--id` to pick one, `--json` for the machine-readable report) and keeps files created since, because it only ever writes files. Files git ignores are in no checkpoint, so a restored `package.json` ends with the `install-dependencies` follow-up. ([#49229](https://github.com/expo/expo/pull/49229) by [@expo-tuft[bot]](https://github.com/apps/expo-tuft))

- Add smart follow-ups: `start`, `install`, `status`, `context`, `navigate`, `runtime errors`, `runtime network` and `skills sync` end with up to three state-derived next actions — a `Next:` section for a terminal, a `followups` key in every `--json` payload, and one `cli:followups` JSONL event. Suppressible with `--no-followups` or `EXAGENT_NO_FOLLOWUPS`, and never able to change an exit code. ([#49229](https://github.com/expo/expo/pull/49229) by [@expo-tuft[bot]](https://github.com/apps/expo-tuft))

### 🐛 Bug fixes

- Fix the `jsonl-event` eval grader, which read the event name from `event`/`name`/`type` and so never matched a line written by `2g`, whose field is `_e`. ([#49229](https://github.com/expo/expo/pull/49229) by [@expo-tuft[bot]](https://github.com/apps/expo-tuft))
- Fix every `exagent runtime` command reporting `No target found` against an app on Android. The debugger target selector probed each target with `Runtime.evaluate` and dropped any target that could not answer, but Expo Go for Android answers that call with `-32601`, so the only connected app was always discarded — including for `runtime errors` and `runtime network`, which never evaluate anything. A target that cannot answer the probe is now kept as a fallback instead of dropped, and only a target whose connection fails is skipped; a target that did answer still wins, so `runtime eval` keeps picking the runtime it can drive when several apps are connected. `runtime eval` against a runtime with no evaluate handler now fails with `RUNTIME_EVALUATE_UNSUPPORTED`, which names the cause and the way out, instead of `RUNTIME_EVALUATE_FAILED`, which invited a pointless retry with a longer `--timeout`. ([#49229](https://github.com/expo/expo/pull/49229) by [@expo-tuft[bot]](https://github.com/apps/expo-tuft))

([#49229](https://github.com/expo/expo/pull/49229) by [@expo-tuft[bot]](https://github.com/apps/expo-tuft))
- Record what the debugger protocol actually offers per platform, from a live pass against Expo Go on an Android emulator and an iOS simulator (SDK 57 / React Native 0.86.2): Expo Go on iOS answers every command, while Expo Go for Android ships a JavaScript engine built without the Chrome DevTools Protocol debugger. Android acknowledges `Runtime.enable` and `Network.enable` and then sends no app data at all, and answers `Runtime.evaluate`, `Runtime.getProperties` and `Runtime.callFunctionOn` with `-32601`. The notes live next to the code that depends on them, in `src/runtime/networkCollector.ts` and `src/runtime/cdpClient.ts`. ([#49229](https://github.com/expo/expo/pull/49229) by [@expo-tuft[bot]](https://github.com/apps/expo-tuft))

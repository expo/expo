# Changelog

## Unpublished

### 🛠 Breaking changes

- The plan-first engine is `exagent dev`, and `exagent start` is `expo start`. A command that shares its name with an `expo` command behaves like that command, so `exagent start` probes nothing and plans nothing: it forwards every argument it does not own to `expo start` untouched and syncs agent skills once the dev server is up, which is what `start --passthrough` did. Everything the plan engine owns moved to the new `exagent dev` verb with the same surface — `--plan`, `--yes`, `--json`, `--ios`/`--android`/`--web`, `--no-followups`, `--no-checkpoint`, `--no-agent-skills` — and the flags `--smart` and `--passthrough` are gone from both commands, because neither has a mode to pick any more. A terminal facing a `dev` plan that installs, prebuilds or builds is asked `Run this plan?` once before the first step runs; declining runs nothing and exits 0, `--yes` answers it up front, and a run that cannot be asked (an agent, CI, `--json`) proceeds without a prompt. The follow-up ids of the plan engine changed with it: `start-smart` is now `dev` and `start-plan` is now `dev-plan`, and the `cli:followups` event of a `dev` run names `dev` as its command. ([#49229](https://github.com/expo/expo/pull/49229) by [@expo-tuft[bot]](https://github.com/apps/expo-tuft))
- A capability with several actions is now one colon group, the way `eas-cli` spells its own commands: `runtime eval|errors|network` is `runtime:eval|runtime:errors|runtime:network`, the `skills` actions are `skills:sync|skills:list|skills:show|skills:clean`, and `exagent setup` is `exagent agents:setup`. The checkpoint guardrail is one group too: `exagent checkpoint` still takes the snapshot, `undo --list` is `exagent checkpoint:list`, and the top-level `exagent undo` is **removed** in favor of `exagent checkpoint:undo` (`--id` unchanged, `--list` gone with the command it was on). The colon is canonical and the space form resolves to the same command, so `exagent skills list` keeps working, and a bare group prints its actions unless one of them is the obvious default (`exagent checkpoint` snapshots, `exagent skills` syncs). An action a group does not have fails with `UNKNOWN_ACTION` and the listing of the ones it does, and is never forwarded to `expo`. `exagent --help` now groups the commands by the job they do — Develop, Create, Deployment, Debug a running app, Agent setup, Checkpoints, Expo CLI — instead of listing them alphabetically. Two names moved with the surface: the follow-up id `setup` is now `agents-setup`, and the JSONL event `setup:completed` is now `agents:setup_completed`. ([#49229](https://github.com/expo/expo/pull/49229) by [@expo-tuft[bot]](https://github.com/apps/expo-tuft))
- `exagent context` is **removed**, merged into `exagent status`. `status --json` now carries the raw project probe verbatim under a new top-level `probe` key — the exact object `context --json` printed, minus its own `followups` — alongside the sections it already had, so the Expo Go reasons the `expoGo` section only counts and the fingerprint error the `freshness` section abbreviates are readable in the same report. The two commands shared one probe and differed only in how much of it they printed, and `status` reads that probe anyway, so the brief costs nothing extra. The `install-dev-client` follow-up moved from `context` to `status`, and the `project-context` follow-up of `status` is gone with the command it named; the `project-context` follow-up of a `dev` plan now points at `npx exagent status --json`. ([#49229](https://github.com/expo/expo/pull/49229) by [@expo-tuft[bot]](https://github.com/apps/expo-tuft))
- The `expo` commands `exagent` does not wrap are forwarded to the project's `expo` CLI as a subprocess, so `exagent prebuild --clean` runs `expo prebuild --clean` with the stdio inherited and the exit code forwarded verbatim. Nothing is added to a forwarded run — no probe, no skill sync, no follow-ups — and each forward emits one `cli:expo_passthrough` event naming the command and its arguments. The forwarded set is **fixed**, taken from the command map of `@expo/cli` minus the commands `exagent` wraps: `run`, `run:ios`, `run:android`, `prebuild`, `config`, `export`, `export:web`, `export:embed`, `serve`, `customize`, `lint`, `login`, `logout`, `register`, `whoami`. `expo add` is `expo install` under another name, so `exagent add` is not forwarded either: it is an alias of the `exagent install` wrapper, and gets the same skill sync, impact report and checkpoint. It is not an open-ended fallback: a name in neither `exagent`'s own surface nor that set fails with `UNKNOWN_COMMAND` naming where commands come from, because an unrecognized name is a typo far more often than it is a new `expo` command, and forwarding it made the typo the `expo` CLI's problem to report. ([#49229](https://github.com/expo/expo/pull/49229) by [@expo-tuft[bot]](https://github.com/apps/expo-tuft))
- `exagent <group> <options>` with no action now **fails** instead of printing the group's actions and exiting 0. `exagent runtime --json` used to answer with the listing and a success code, which a driving agent reads as "that worked" before waiting for output that is never coming; it now prints the listing, then `UNKNOWN_ACTION` naming the actions those options could have belonged to, `Try: npx exagent runtime --help`, and exits 1. A bare group is unchanged — `exagent runtime` still lists its actions and exits 0 — as is `<group> --help`, and a group with a default action still gets its options: `exagent checkpoint --label x` snapshots. Two conventions ride with it (`llp/0010`): the exit codes of every command now come from one table — 0 success, 1 the tool did not work, 7 a person must finish the step, 20/21/22 the operation failed, was canceled, or timed out — and a command group named after a forwarded `expo` command keeps the forwarded behaviour for its bare form and owns only its colon forms, so a future `config:*` group cannot take `exagent config` away from `expo config`. A forwarded subprocess's code is still handed back verbatim; the one shipped command re-coded since is the `deploy` auth failure, below. ([#49229](https://github.com/expo/expo/pull/49229) by [@expo-tuft[bot]](https://github.com/apps/expo-tuft))
- `exagent dev` is a command **group** now, so that `dev:wait` could join it, and `exagent dev --help` prints the group's actions instead of the plan engine's options. Running the command is unchanged: `dev` declares `run` as its default action, so `exagent dev`, `exagent dev --plan --ios` and every other invocation still run the plan engine with every option they were given. Only help moved one hop — the `--plan`/`--yes`/`--json` block is `exagent dev:run --help` — which is what `<group> --help` has always meant for `checkpoint` and `skills` (`llp/0010` §Registry rules). ([#49229](https://github.com/expo/expo/pull/49229) by [@expo-tuft[bot]](https://github.com/apps/expo-tuft))

- A command that stops on a step only a person can complete now exits **7** instead of 1, and ends with a three-line handoff naming what its user has to do. It reaches two shipped failures of `exagent deploy`: the launch CLI refusing for lack of a login (`LAUNCH_NOT_AUTHENTICATED`) and an `eas deploy` that stopped on an account or a prompt (`EAS_DEPLOY_FAILED`), plus an `expo export` that stopped on a prompt (`EXPORT_FAILED`). The codes are unchanged; only the exit code and the last lines of output are. Anything that treated a non-zero exit from those commands as "the call was wrong" now has a third answer to read: 0 the tool worked, 1 the tool did not work, 7 the tool worked and is waiting on a human. ([#49229](https://github.com/expo/expo/pull/49229) by [@expo-tuft[bot]](https://github.com/apps/expo-tuft))

### 🎉 New features

- Initial `exagent` package: `skills` command group (`skills:sync`, `skills:list`, `skills:show`, `skills:clean`) ported from the `@expo/cli` proof-of-concept. ([#49229](https://github.com/expo/expo/pull/49229) by [@expo-tuft[bot]](https://github.com/apps/expo-tuft))
- Add `exagent dev` and `exagent dev --plan`: decide between `expo start`, `expo prebuild`, and `expo run:*` from the project state, emit the plan with time-class estimates, then run it or exit without running it. ([#49229](https://github.com/expo/expo/pull/49229) by [@expo-tuft[bot]](https://github.com/apps/expo-tuft))
- Add the project-state probe with the Expo Go compatibility check, reported verbatim as the `probe` key of `exagent status --json` (the machine-readable project brief), and the post-install impact report of `exagent install` (`--no-impact` to skip it). ([#49229](https://github.com/expo/expo/pull/49229) by [@expo-tuft[bot]](https://github.com/apps/expo-tuft))
- Add `exagent runtime:eval` and `exagent runtime:errors`: evaluate JavaScript in the running app and collect its runtime errors over the dev server's debugger connection, with app output fenced in untrusted-content markers and `--json` for the machine-readable shape. ([#49229](https://github.com/expo/expo/pull/49229) by [@expo-tuft[bot]](https://github.com/apps/expo-tuft))
- Add `exagent runtime:network`: collect the HTTP requests the running app makes over a time window, one line per request with its status and content type, fenced in untrusted-content markers (`--duration` for the window, `--json` for the machine-readable shape). A request the runtime answered, one it reported as failed, and one it never answered are three separate outcomes, because React Native reports a connection error to JavaScript without sending `Network.loadingFailed`. When the connected runtime does not implement the debugger's Network domain — still an unstable part of React Native — the command reports `NETWORK_DOMAIN_UNAVAILABLE` and points at `exagent runtime:errors`, instead of printing an empty list that reads like "the app made no requests". ([#49229](https://github.com/expo/expo/pull/49229) by [@expo-tuft[bot]](https://github.com/apps/expo-tuft))
- Add `exagent status`: a read-only, `git status`-like overview of the project, the Expo Go verdict, the freshness of the last recorded development build per platform, the dev server and the apps connected to it, the linked agent skills, and the command that would get the app onto a device (`--json` for the machine-readable report, `--dev-server-url` to probe another dev server). ([#49229](https://github.com/expo/expo/pull/49229) by [@expo-tuft[bot]](https://github.com/apps/expo-tuft))
- Add `exagent navigate <route>`: open a route as a deep link on the booted simulator or attached device, resolving the URL shape from the app connected to the dev server (`exp://` for Expo Go) and the `scheme` field of the app config (`--scheme` to override). ([#49229](https://github.com/expo/expo/pull/49229) by [@expo-tuft[bot]](https://github.com/apps/expo-tuft))

- Add `exagent agents:setup`: link the agent skills of the installed packages, then create or update one managed block in the project's `AGENTS.md` with the project facts from the probe and the command cheat sheet (`--agent` to pick the agents, `--no-agents-md` and `--no-agent-skills` to skip either half, `--json` for the machine-readable report). Content outside the block markers is preserved byte for byte, and `CLAUDE.md` is never written. ([#49229](https://github.com/expo/expo/pull/49229) by [@expo-tuft[bot]](https://github.com/apps/expo-tuft))

- Add `--json` to `exagent navigate`: print the opened URL, how it was resolved, the target app, the device, the device command and its exit code as one JSON object on stdout. ([#49229](https://github.com/expo/expo/pull/49229) by [@expo-tuft[bot]](https://github.com/apps/expo-tuft))

- Add `exagent new <directory>`: create a project with no TTY attached, by running `create-expo` as a subprocess with every prompt answered (`--name` to set the display name in `app.json`, `--no-install`, `--no-git`, `--json` for the machine-readable report). It initializes a git repository when `create-expo` left none and the project is not already inside one, and forwards the exit code of a failed scaffold. ([#49229](https://github.com/expo/expo/pull/49229) by [@expo-tuft[bot]](https://github.com/apps/expo-tuft))

- Add `exagent deploy`: ship the web app to EAS Hosting (`expo export --platform web`, then `eas deploy --non-interactive`) and the native app through launch.expo.dev by running `create-launch --json` as a subprocess (`--web`/`--native` to pick the targets, both at once for a cross-platform deploy, `--json` for the machine-readable report). With no target flag, a project that depends on `react-native-web` deploys its web app. The launch CLI packs and uploads the project source as the signed in Expo user and answers with the launch URL that finishes the job in a browser; `exagent` resolves it from the project, then `PATH`, then `npx create-launch@latest`, prints its progress as it happens, and hands the URL over as the required next step. `--upload-root <dir>` uploads a monorepo, which runs the launch CLI from that directory with `--project <app>`. Failures keep the words of the tool that produced them, with the missing-login case mapped to `LAUNCH_NOT_AUTHENTICATED` and handed back to a person as a needs-human stop. ([#49229](https://github.com/expo/expo/pull/49229) by [@expo-tuft[bot]](https://github.com/apps/expo-tuft))

- Add `exagent checkpoint` and `exagent checkpoint:undo`: snapshot the project before a change, and put the snapshot back. A checkpoint is written with git plumbing against a temporary index (`git add -A` → `git write-tree` → `git commit-tree`), so it commits nothing onto the user's branch and leaves `HEAD`, the branches, the reflog, and the index untouched; the object ids are recorded in `.expo/exagent-checkpoints.json`, capped at the 20 most recent. `exagent install`, `exagent agents:setup` and an `exagent dev` plan that prebuilds each take one before they change anything, best-effort and never able to fail the command (`--no-checkpoint` or `EXAGENT_NO_CHECKPOINT` to skip it). `exagent checkpoint:undo` restores every file of a checkpoint (`exagent checkpoint:list` for the recorded ones, `--id` to pick one, `--json` for the machine-readable report) and keeps files created since, because it only ever writes files. Files git ignores are in no checkpoint, so a restored `package.json` ends with the `install-dependencies` follow-up. ([#49229](https://github.com/expo/expo/pull/49229) by [@expo-tuft[bot]](https://github.com/apps/expo-tuft))

- Add the dev-server lock: while `exagent start` or `exagent dev` runs a dev server, it listens on a socket for the project — `.expo/exagent-dev-server.sock`, or a named pipe derived from the project path on Windows — and answers one JSON line naming the dev server's URL, port and PID. `exagent status` and `exagent runtime:eval|errors|network` ask it before anything else, so a dev server that had to walk past a busy 8081 is found instead of missed; the `runtime` commands used to assume 8081 whenever `--dev-server-url` was absent. A socket rather than a file, on purpose: nothing answers unless the process holding it is alive, so there is no record that can go out of date, no PID to check, and no way to read the port of a dev server that has already stopped. The URL a lock names is still probed and never trusted — the lock proves the wrapper is alive, and the probe proves the dev server is. The published port is the one the dev server itself reports in `.expo/dev/logs/start.log` (`metro:instantiate`, only entries newer than the spawn), falling back to `--port` and then 8081 if it never reports one, and the lock is released when the dev server exits. A lock that cannot be taken never affects the dev server: another `exagent` already holding the address is reported as `cli:dev_lock_skipped` and any real failure as one warning, while `cli:dev_lock_acquired` and `cli:dev_lock_zombie_replaced` name what happened for a driving agent. A dev server started by `expo start` directly holds no lock and is still found the old way, from the port in the log and then a short port scan, and `--dev-server-url` keeps skipping discovery entirely. ([#49229](https://github.com/expo/expo/pull/49229) by [@expo-tuft[bot]](https://github.com/apps/expo-tuft))

- Add `exagent build:wait <build-id>`: attach to an EAS build that already exists — one started by CI, by the dashboard, or by another agent — and exit with what it did. It polls `eas build:view <id> --json` as a subprocess (`--submission` polls `eas submit:view` instead) and its answer is the **exit code**, per the convention of `llp/0010`: `0` finished, `20` errored, `21` canceled or interrupted, `22` the timeout expired while the build was still running, `1` the command could not do its job. `--timeout` (default 45m) and `--interval` (default 10s, backing off to 30s after 5m) take a duration in milliseconds or with a unit — `90s`, `30m`, `2h` — which every flag that waits now accepts. Progress goes to the JSONL event stream as `cli:build_wait_poll` with the queue position and the estimated wait, never to stdout, so `--json` still prints exactly one object: the outcome, the status, the platform and profile, how long it waited and how many times it asked, and the build's error, artifacts, fingerprint, metrics and versions. A status the CLI has never seen keeps the wait polling rather than ending it, `PENDING_CANCEL` included, because ending on an unknown status would report an outcome nobody observed; three failed polls in a row end the wait as a tool error with `Try: npx eas workflow:status <id> --wait --json`, since a build id and a workflow id look alike; and Ctrl-C ends it promptly instead of after the current sleep. The new `build` group has no default action on purpose: `exagent build --platform ios` is a correct command aimed at the wrong CLI, so it fails with `UNKNOWN_ACTION` and `Try: npx eas build --platform ios` — the caller's own flags on the command that does start a build — rather than printing a listing that reads like success. ([#49229](https://github.com/expo/expo/pull/49229) by [@expo-tuft[bot]](https://github.com/apps/expo-tuft))

- Add `exagent config:effective`: what the config plugins actually produced for each platform, read from `expo config --type introspect --json` run as a subprocess. Introspection compiles the plugins in memory and writes nothing to the project, so the command is read-only. The report is the mods per platform, the plugins that ran joined with the `plugins` array of the static app config so an auto-applied plugin is told apart from a declared one, the autolinked modules, and `notAttributable` — `ios.xcodeproj` and the dangerous mods, which introspection drops, so their absence means "not answered" rather than "unchanged". The default output is counts per mod, because the values are kilobytes of plist and XML; `--file <name>` prints one native file (`infoPlist`, `entitlements`, `expoPlist`, `podfileProperties`, `manifest`, `gradleProperties`, `strings`, `colors`, `colorsNight`, `styles`) and `--json` prints all of them. `--platform <ios|android|all>` narrows it, and one `cli:config_effective` event carries the counts and never a value. A payload with no `_internal.modResults` — an older CLI, or a run that failed before the plugins compiled — fails with `CONFIG_INTROSPECT_UNSUPPORTED` naming what to run by hand. `exagent config` on its own is still `expo config`: the group owns its colon forms only, per the registry rule of `llp/0010`. ([#49229](https://github.com/expo/expo/pull/49229) by [@expo-tuft[bot]](https://github.com/apps/expo-tuft))

- Add `exagent doctor:check` (and `exagent doctor`, which runs it): run `expo-doctor --verbose` as a subprocess — the project's own copy first, then `npx expo-doctor` — and normalize its report into the checks that ran, what each failing one found, and the advice it gave. expo-doctor has no `--json` and no stable check ids, so the report is read back out of its prose and says how well that went: `parse` is `full`, `best-effort` or `failed`, and `raw` always carries everything the tool printed, so nothing the parse missed is lost. The exit code is expo-doctor's own, which is 1 when any check failed; the one exception is a 127 with nothing parsed, which is the shell's "command not found" and so a verdict on the machine rather than on the project — that becomes `EXPO_DOCTOR_NOT_FOUND` with the install step attached. Since `exagent doctor:fix` does not exist yet, the follow-ups are the actions the failing checks themselves named, pulled out of their advice (`--no-followups` to leave them out). One `cli:doctor_check` event carries the counts and the parse quality. ([#49229](https://github.com/expo/expo/pull/49229) by [@expo-tuft[bot]](https://github.com/apps/expo-tuft))

- Add smart follow-ups: `start`, `dev`, `install`, `status`, `navigate`, `runtime:errors`, `runtime:network` and `skills:sync` end with up to three state-derived next actions — a `Next:` section for a terminal, a `followups` key in every `--json` payload, and one `cli:followups` JSONL event. Suppressible with `--no-followups` or `EXAGENT_NO_FOLLOWUPS`, and never able to change an exit code. ([#49229](https://github.com/expo/expo/pull/49229) by [@expo-tuft[bot]](https://github.com/apps/expo-tuft))

- Add `exagent dev:wait`: wait until the dev server has finished bundling, then say whether the bundle is this project's and whether an app is running it (`--timeout` for the budget, default two minutes, `--require-app` to also wait for an app to attach, `--dev-server-url` to wait on a named dev server, `--json` for the machine-readable report). It holds one long-lived `GET /status` request open rather than polling, because the dev server answers that request only once its bundler is done; the `X-React-Native-Project-Root` header it flushes first is what finally answers "is this dev server mine?", which a port scan never could. The exit code is the answer a driving agent branches on: `0` ready, `22` the wait expired and is worth repeating with a longer `--timeout`, `20` something answered that is not an Expo dev server, `1` there was no dev server to wait on. One `cli:dev_wait` event carries the same report. `exagent status` gains the same facts, without ever waiting for a bundle: its `devServer` section now reports `source` (which discovery step found the dev server — `flag`, `lock`, `log`, `default` or `scan`), `ready` (`null` while the bundler is still working, because status never blocks), and `projectRootMatched`. ([#49229](https://github.com/expo/expo/pull/49229) by [@expo-tuft[bot]](https://github.com/apps/expo-tuft))

- Add the needs-human handoff protocol: when a command reaches a step only a person can finish, it exits 7, prints `Needs a human <scenario>` / `Ask the user <command>` / `Or set <ENV>`, and emits one `cli:needs_human` JSONL event carrying the scenario, the exact command or URL, the environment variables that remove the need on an unattended machine, whether re-running resumes, and how it was recognised; `cli:error` gains a `needsHuman` boolean for consumers reading only that. Thirteen scenarios live in one data table — the two logins, Apple auth, App Store Connect keys, iOS and Android credentials, device registration, the launch browser step, and the prompts of both CLIs — and a stop is noticed in four ways: `eas whoami` asked up front, `CI=1` in every captured `expo` subprocess so a prompt fails fast instead of hanging, the stderr of a failed run matched against the table, and, when a caller opts in, a child that goes silent on a question being killed after `EXAGENT_PROMPT_TIMEOUT_MS` (default 20s) with the question quoted back. A CLI whose output is inherited keeps its terminal and is never touched. ([#49229](https://github.com/expo/expo/pull/49229) by [@expo-tuft[bot]](https://github.com/apps/expo-tuft))

- Fix `exagent dev --yes`, the documented non-interactive entry point, on a busy port. It used to print its plan as JSON, hand stdout to the `expo start` subprocess — which appended raw log lines after the closing brace, so `JSON.parse` failed outright — then exit **1** having started no dev server at all, while its own follow-ups told the caller to open a URL on port 8081, which belonged to whatever other project already held it. Three changes: in `--json` mode the plan's subprocesses are captured and stdout carries exactly one object, printed when the run ends (the plan with its follow-ups, or the error envelope; `dev --plan --json` is unchanged, and the plan still reaches an agent first on the `cli:start_plan` event). A step that stops because the Expo CLI needs an answer is now a needs-human failure — exit **7**, the handoff block, a `cli:needs_human` event, and a message naming `--port` as the way to answer the port question up front — in `--json` runs and in any other run with no terminal, where the output is teed instead of inherited so the stop can be recognised. And the follow-ups of a run name the port the dev server actually reported: when nothing reported one, they say so and point at `exagent status` instead of guessing at 8081. A person at a real terminal still gets the tools' own stdio, unchanged. ([#49229](https://github.com/expo/expo/pull/49229) by [@expo-tuft[bot]](https://github.com/apps/expo-tuft))

- Add `--port <number>` to `exagent dev` and `exagent dev:run`, forwarded to the `expo start` the plan ends with. It is the answer to the one question this command cannot be asked: when 8081 is busy the Expo CLI asks whether to use another port, and a run with no terminal stops there and starts nothing. Naming the port answers it before it is asked, and the follow-ups then name the dev server that actually started. The flag was always forwarded — it is one of `expo start`'s — but it was in no help text, so the only documented way to choose a port was to leave `exagent dev` for `exagent start`. An unusable value is now reported by this command, before anything runs, instead of by the bundler a minute later. ([#49229](https://github.com/expo/expo/pull/49229) by [@expo-tuft[bot]](https://github.com/apps/expo-tuft))

- Add `--json` to `exagent install`: one object carrying what the human output already knows — the packages, whether they were installed, the exit code, the impact classification, the checkpoint that was taken (`id` and file count), which of the installed packages ship an agent skill, and the follow-ups. `--json` used to be forwarded to `expo install`, which rejects it outside `--check`, so the one common agent action had no machine-readable result; the flag is this wrapper's own now, except in a `--check` run, where the Expo CLI's report is carried verbatim under `check`. Nothing but that object reaches stdout in this mode: the `expo install` subprocess is captured and its output goes to stderr, and the checkpoint line, the impact table and the skill-sync notice stay quiet. Arguments are also validated **before** the checkpoint is taken, against the flags both CLIs accept — a rejected invocation used to leave a snapshot of an install that never ran — and `--check` is documented in `install --help`, where the errors already named it. ([#49229](https://github.com/expo/expo/pull/49229) by [@expo-tuft[bot]](https://github.com/apps/expo-tuft))

- Add the `--json` error envelope: a command invoked with `--json` now prints one JSON object on stdout whether it succeeded or failed, and a failure is `{"error": {"code", "message", "suggestedCommand", "needsHuman"}}` — the code the site already shipped, the prose verbatim, the `Try:` command, and the whole needs-human record when a person has to finish the step (`null` for both when they do not apply, so the key set never varies). Every error path used to print zero bytes on stdout under `--json`, which left an agent that had committed to parsing it scraping English out of stderr; the prose has not moved and still goes to stderr, unchanged. The group listing that accompanies an `UNKNOWN_ACTION` moves to stderr under `--json` for the same reason: stdout holds the envelope and nothing else. ([#49229](https://github.com/expo/expo/pull/49229) by [@expo-tuft[bot]](https://github.com/apps/expo-tuft))

- Add an `auth` section to `exagent status`: who the Expo CLI family acts as on this machine, from `eas whoami` with a short deadline, falling back to the presence of `EXPO_TOKEN` when there is no CLI to ask (`{ loggedIn, user, source }` in `--json`). "Unknown" is kept apart from "not signed in", because the two lead to different next actions, and a probe that fails costs the section rather than the command — status still exits 0. ([#49229](https://github.com/expo/expo/pull/49229) by [@expo-tuft[bot]](https://github.com/apps/expo-tuft))

### 🐛 Bug fixes

- Fix `exagent dev` starting a dev server that never sees an edit, which made the entry-bundle check of `exagent dev:wait` certify code the caller had already replaced. A run with no terminal spawned `expo start` with `CI=1`, and `CI` does two jobs in the Expo CLI: it makes prompts fail fast, and it turns Metro's file watcher off (`Metro is running in CI mode, reloads are disabled`). Only the first was wanted. Without a watcher the dev server serves the snapshot it read at start-up forever, so an agent could append a syntax error to a route and get `bundle.ok: true` and exit 0 from `dev:wait` — the failure the bundle check exists to prevent, on the command the CLI recommends everywhere. The dev-server step (`expo start`, `expo run:ios`, `expo run:android`) is now spawned with `CI` untouched, and the prompts still fail fast because the other half was never the variable: the CLI's `isInteractive()` also requires a TTY on stdout, and a captured child's stdout is a pipe. `exagent dev --yes` on a busy port still exits **7** with the needs-human handoff in about a second, and nothing is set to `CI=0` — a machine whose own environment says `CI` keeps the behaviour it asked for. Every other captured `expo` step (`expo prebuild`, `expo export`, `expo install`) is unchanged. - Fix `exagent runtime:errors` reporting stacks nobody can read, and exiting 0 with the app throwing. Every frame was an offset into the bundle with the whole transform query string attached — roughly 2 KB of repeated `&transform.…` per error, and no project file anywhere. Each stack is now sent to the dev server's `/symbolicate` endpoint and comes back as project files and lines (`at wave3bBoom (src/app/index.tsx:101:18)`), with the frames also carried structurally under `frames` and a `symbolicated` flag saying whether any frame was mapped. - Fix `exagent runtime:eval` never settling a promise, so every async check came back as the promise polyfill's internal fields (`{_A,_x,_y,_z}`) and `--no-await-promise` did nothing at all. CDP's `awaitPromise` only awaits a result the runtime tagged `subtype: "promise"`, and React Native replaces the engine's `Promise` with a JavaScript polyfill the inspector sees as an ordinary object — so `fetch`, an AsyncStorage read and a store selector were all opaque. The promise is now settled inside the app: the expression is wrapped so the app detects a thenable, subscribes to it and parks the outcome under a per-run nonce, and the CLI polls that over the same debugger connection until it settles or `--timeout` runs out. A value that is not a thenable is untouched — one round trip, and the type the runtime reported. `--json` gains a `promise` key with `state`, `awaited` and how long the wait took; a resolved promise puts its settled value on `value` with `type` describing that value; a rejection is `promise.state: "rejected"` with the reason, leaves `threw` false because the expression returned normally, and exits **1** like a throw, so an agent gating on the exit code cannot read a failed request as a pass. A promise still pending when the wait ends is `RUNTIME_PROMISE_PENDING` rather than a value, and the app is told to drop what it was holding. `--no-await-promise` is real now: it reports the pending promise without waiting, and exits 0. One behaviour changed with it — the expression is evaluated inside a function, so a *statement* such as `var x = 1` stops compiling there and is re-run exactly as written, which is what it did before.

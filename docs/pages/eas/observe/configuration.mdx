Configure Expo Observe at runtime to fit your app's build setup, environment, and data routing. This page covers enabling metrics in development, sampling, ignoring selected metrics and events, using a custom endpoint, separating data by environment, asking for user consent, and turning off data ingestion from the dashboard. For the runtime methods themselves, see the [`configure()`](/versions/latest/sdk/observe/#configureconfig) and [`dispatchEvents()`](/versions/latest/sdk/observe/#dispatchevents) API references.

## Sampling

By default, every installation dispatches its metrics. For high-volume apps, you can sample a fraction of installations by setting `sampleRate` to a value between `0` and `1`:

```tsx
import { Observe } from 'expo-observe';

// Dispatch metrics from ~25% of installations.
Observe.configure({
  sampleRate: 0.25,
});
```

The sampling decision is **deterministic per installation**. Each installation is either permanently in-sample or out-of-sample for a given rate, so the choice is stable across app launches and you get a consistent slice of installations rather than a random subset of sessions.

A few details worth knowing:

- Values outside the `[0, 1]` range are clamped to the nearest edge. `0` always drops; `1` always dispatches.
- Out-of-sample devices drop pending metrics rather than accumulating them. Lowering the rate later does not retroactively send earlier sessions.
- Sampling depends on [`dispatchingEnabled`](/versions/latest/sdk/observe/#observeconfig). If `dispatchingEnabled` is `false`, nothing is dispatched regardless of `sampleRate`.

### Sample errors separately

To keep more errors than other events, set `errorSampleRate`. Errors include unhandled JavaScript errors, errors from `reportError` and `ObserveErrorBoundary`, and native crash reports. All other events follow `sampleRate`:

```tsx
import { Observe } from 'expo-observe';

// Dispatch metrics from ~3% of installations, and errors from all installations.
Observe.configure({
  sampleRate: 0.03,
  errorSampleRate: 1,
});
```

`errorSampleRate` is a minimum. Installations in-sample for `sampleRate` always send errors. A lower value has no effect, and `configure()` prints a warning. An unset `sampleRate` counts as `1`.

## Ignore metrics and events

If you don't use some metrics or events, skip them with `ignoredMetrics` and `ignoredEvents` to send less data:

```tsx
import { Observe } from 'expo-observe';

Observe.configure({
  ignoredMetrics: ['expo.app_startup.tti'],
  ignoredEvents: ['reanimated.warning', 'checkout.completed'],
});
```

`ignoredMetrics` matches metric names such as `expo.app_startup.tti`. `ignoredEvents` matches event names, including custom names passed to [`Observe.logEvent`](/eas/observe/events/). Ignored data is still recorded on the device but never sent.

## Enable metrics in development

By default, metrics collected from debug builds are not dispatched. To dispatch them anyway (for example, while testing your Expo Observe integration), set `dispatchInDebug` to `true` when calling `configure()`:

```tsx
import { Observe } from 'expo-observe';

Observe.configure({
  dispatchInDebug: true,
});
```

A build is treated as a debug build if either the native app is a debug build or the JS bundle is a development bundle (`__DEV__` is `true`). This detection is independent of the `environment` value (see [Environments](#environments)).

`dispatchInDebug` has no effect on release builds, which always dispatch (subject to [`dispatchingEnabled`](/versions/latest/sdk/observe/#observeconfig) and [`sampleRate`](#sampling)). If `dispatchingEnabled` is `false`, nothing dispatches regardless of `dispatchInDebug`. `sampleRate` and `errorSampleRate` also apply in debug builds.

> **warning** Enable this only when testing your Expo Observe integration. Development/debug performance differs significantly from production, so collecting development/debug metrics may distort the results shown in your dashboard.

## Custom endpoint

Expo Observe sends data using the OpenTelemetry Protocol (OTLP) over HTTP with a JSON payload. It posts metrics to `<endpointUrl>/<project-id>/v1/metrics` and logs to `<endpointUrl>/<project-id>/v1/logs`, where `<project-id>` is your Expo Services project ID. This means you can set `endpointUrl` to an OpenTelemetry-compatible backend or an OpenTelemetry Collector to route your observability data there.

To change the endpoint, set the `endpointUrl` value in your **app config**:

```json app.json
{
  "expo": {
    "extra": {
      "eas": {
        "observe": {
          "endpointUrl": "https://your-custom-endpoint.com"
        }
      }
    }
  }
}
```

The endpoint URL is baked into the native layer of the app at build time, so changing it requires regenerating native code. After updating your app config, run `npx expo prebuild` and create a new build to apply the change.

The path includes your project ID before the standard `/v1/metrics` and `/v1/logs` OTLP paths. If your backend expects the standard OTLP path without that prefix, send the data to an OpenTelemetry Collector that receives it and re-exports it to your backend.

## Environments

All metrics are grouped by environment. The environment value is derived from `process.env.NODE_ENV` by default (falling back to `'production'` if unset). To override it, use [`configure({ environment })`](/versions/latest/sdk/observe/#configureconfig).

The environment is a metadata tag attached to each metric and is independent of how the bundle was built. To control whether debug-build metrics are dispatched, see [Enable metrics in development](#enable-metrics-in-development). To disable all dispatching globally, use `configure({ dispatchingEnabled: false })`.

## Network traces

> **info** Network traces require SDK 58 and later.

Completed network requests can be recorded as trace spans. Recording is off by default, because each span counts toward your event quota. Turn it on with:

```ts
import { Observe } from 'expo-observe';

Observe.configure({ networkTraces: true });
```

Pass an object to record only the requests you care about. Hosts match exactly and case-insensitively, so subdomains are not implied. An omitted field matches every request, and an empty array matches none:

```ts
Observe.configure({
  networkTraces: { filter: { hosts: ['api.myapp.com'], methods: ['GET', 'POST'] } },
});
```

The object form records unless you say otherwise, so set `enabled: false` to keep a filter configured while recording nothing.

A request that is turned off or filtered out never reaches the local database, so nothing is stored and nothing is exported. The setting applies to future requests, so spans recorded earlier in the launch are still sent. It also persists across launches, so requests observed before `configure` runs on the next launch follow the last value you set.

Because the value persists, removing the option takes effect the next time `configure` runs, not immediately. The same applies to a narrow `hosts` list: it keeps suppressing early-startup requests until a `configure` widens it.

URLs are redacted before they are stored. A username and password in the URL are replaced with `REDACTED`, as are the query parameters `AWSAccessKeyId`, `Signature`, `sig`, `X-Amz-Signature`, `X-Amz-Credential`, `X-Amz-Security-Token`, and `X-Goog-Signature`. A secret in any other query parameter is stored as-is.

## Ask for user consent

By default, Expo Observe collects data from the first launch. If your app must ask the user before it collects data, keep Expo Observe inactive until the user grants consent.

Set the `consent` value in your **app config** to `'not-granted'`:

```json app.json
{
  "expo": {
    "extra": {
      "eas": {
        "observe": {
          "consent": "not-granted"
        }
      }
    }
  }
}
```

The value is `'granted'` or `'not-granted'`, and the default is `'granted'`. Any other value keeps Expo Observe inactive and logs a warning. The value is embedded in the native app at build time, so a change needs a new build. An update from EAS Update does not change it.

When the user makes a choice, call `Observe.setConsent()` on Android or iOS:

```tsx
import { Observe } from 'expo-observe';

await Observe.setConsent(userAccepted ? 'granted' : 'not-granted');
```

The device saves the value. On later launches, the saved value overrides the app config value.

### While consent is not granted

- Expo Observe does not write data to the device and does not send data.
- `Observe.clientId` is `null`, and Expo Observe does not create the [client ID](/eas/observe/reference/client-id/).
- Startup metrics of the current launch stay in memory. A grant in the same launch saves them.
- `configure()` still saves its settings on the device. The settings do not contain user data.

On iOS, Expo Observe also stays inactive for a launch when it cannot read the saved value, for example before the first unlock after a device restart. That launch keeps the data that is already stored.

### Grant and revoke

A grant starts collection in the current launch. Native crashes from before the grant are not reported.

A revoke stops collection and deletes the Expo Observe data that is stored on the device. A revoke keeps the client ID, because other Expo libraries use the same ID.

Expo Observe starts collection at most one time in each app launch. After a revoke, a grant only saves the value, and collection starts at the next launch.

A revoke does not stop work that already started:

- A request that is in progress can finish and deliver its data.
- A record or crash file that is written at the same time as the revoke can stay on the device. The next launch without consent deletes it.

`setConsent()` rejects when the device cannot save the value, for example when the storage is full. After a failed revoke, collection stops and the stored data is deleted, but the next launch can read the earlier value. After a failed grant, nothing changes. In both cases, call `setConsent()` again.

`AppMetrics.clearStoredEntries()` does not change consent. It also deletes the sessions of the current launch, so the data that those sessions record after the call is lost. To delete the data when the user withdraws consent, call `setConsent('not-granted')`.

### Consent and `dispatchingEnabled`

`configure({ dispatchingEnabled: false })` stops only the upload. Expo Observe still collects data and stores it on the device. Consent also stops collection and storage, and a revoke deletes the stored data. Use consent when the user must agree before Expo Observe collects data.

## Turn off data ingestion

The options above control what your app sends. You can also stop Expo Observe from accepting data on the server side, without shipping an app update, using the **Observe data ingestion** toggle in the Expo dashboard:

- **Account level**: open [Account settings](https://expo.dev/accounts/[account]/settings) and turn off **Observe data ingestion**. This pauses ingestion for all projects in the account.
- **Project level**: open [Project settings](https://expo.dev/accounts/[account]/projects/[project]/settings) and turn off **Observe data ingestion**. This pauses ingestion for that project only.

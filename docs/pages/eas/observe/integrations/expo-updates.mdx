[`expo-updates`](/versions/latest/sdk/updates/) library writes its errors and warnings to a log on the device. Without this integration, you must add code to read and send that log, and ship a new build or update, before you can see a problem in production. The `expo-updates` integration for EAS Observe reports the log errors as Observe errors, and optionally the log warnings as events. It also reports the JS crashes that [error recovery](/eas-update/error-recovery/) handled, which happen soon after launch or before the first render.

## Prerequisites

<Prerequisites>
  <Requirement title="Expo SDK 58 or later">
    The integration is available in `expo-observe` version 58.0.17 and later. Use `expo-updates`
    version 58.0.19 or later on Android and iOS. With an earlier version on Android, the
    integration reports a JS error that error recovery handled as `updates.error` with the
    `Unknown` code, not as `updates.error_recovery`. With an earlier version on iOS, the
    integration reports emergency launch and initialization errors as `updates.error_recovery`,
    and `ignoredCodes` and `shouldReport` cannot skip them.
  </Requirement>
  <Requirement title="An app already using EAS Observe">
    Follow [Get started](/eas/observe/get-started/) to install `expo-observe` and create your first
    build.
  </Requirement>
  <Requirement title="expo-updates installed in the app">
    The integration reads the log of [`expo-updates`](/versions/latest/sdk/updates/). If
    `expo-updates` is not installed, the integration prints a warning and does nothing.
  </Requirement>
</Prerequisites>

## Enable the integration

Call `Observe.configure()` once with the `expo-updates` integration flag at module scope, before your app mounts:

```tsx src/app/_layout.tsx
import { Observe } from 'expo-observe';

Observe.configure({
  integrations: { 'expo-updates': true },
});
```

## How it works

When `Observe.configure()` runs, the integration reads the `expo-updates` log entries written since its last report. `expo-updates` keeps log entries for one day, so on the first run, the integration reads up to one day back. Because the integration reads the log at the next launch, it also reports errors from an earlier launch. For example, it reports a crash that error recovery handled before the app could start again.

The integration reports the entries as follows:

- An `error` or `fatal` entry becomes an Observe error named `updates.error`. The error message is the entry's code followed by the log message, for example `UpdateFailedToLoad: ...`.
- A JS error that error recovery handled becomes an Observe error named `updates.error_recovery`. The message includes the original JS error. The same error can also appear as an unhandled JavaScript error.
- When error recovery cannot recover, it logs an entry and then crashes the app. The integration does not report that entry, because Observe reports the crash itself.
- A `warn` entry becomes an `updates.warning` event with `warn` severity, but only when `reportWarnings` is `true`.
- The integration does not report entries with a lower level.

A reported error gets the current session and time, not the time of the log entry. Warning events keep the log entry time in the `logTimestamp` attribute.

To limit the number of reports, the integration reports each distinct message at most once every 15 minutes. It reports at most 20 distinct errors and 20 distinct warnings in any 15-minute period. JS errors that error recovery handled skip the filters and have their own limit of 20 distinct messages, so other errors cannot stop them from being reported. The limits reset when the app restarts.

**Warning event attributes:**

| Attribute      | Type     | Description                                                           |
| -------------- | -------- | --------------------------------------------------------------------- |
| `message`      | `string` | The log message, cut to 500 characters.                               |
| `code`         | `string` | The log entry code, for example `AssetsFailedToLoad`.                 |
| `logTimestamp` | `number` | The time the entry was written, in milliseconds since the Unix epoch. |
| `updateId`     | `string` | The ID of the update that the entry is about, if there is one.        |
| `assetId`      | `string` | The ID of the asset that the entry is about, if there is one.         |

## Configuration

Pass a configuration object instead of `true` to change what the integration reports:

```tsx src/app/_layout.tsx
import { Observe } from 'expo-observe';

Observe.configure({
  integrations: {
    'expo-updates': {
      reportWarnings: true,
      ignoredCodes: ['NoUpdatesAvailable'],
      shouldReport: entry =>
        !entry.message.includes('The Internet connection appears to be offline'),
    },
  },
});
```

- `reportWarnings`: Whether the integration also reports warnings as `updates.warning` events. The default is `false`.
- `ignoredCodes`: Log entry codes that the integration does not report. The default is an empty list.
- `shouldReport`: A function that gets each log entry and returns `false` to skip it. It runs after `ignoredCodes`. If the function throws, the integration reports the entry.

`ignoredCodes` and `shouldReport` do not apply to JS errors that error recovery handled.

Some errors are common and expected, for example a failed update check when the device is offline. `expo-updates` logs network errors with codes that it also uses for other errors, such as `UpdateFailedToLoad` on Android and `Unknown` on iOS. On iOS, the message includes the network error, so a `shouldReport` function can check the message to skip only the network errors. On Android, the message does not include the network error.

## View errors and events

In the dashboard: open your project and navigate to **Observe**. Errors from the integration are named `updates.error` and `updates.error_recovery`, and warnings are `updates.warning` events.

From the CLI:

<Terminal
  cmd={[
    '# Show errors',
    '$ eas observe:errors',
    '',
    '# Show expo-updates warning events',
    '$ eas observe:events updates.warning',
  ]}
/>

For naming, severity, and attribute details shared by all events, see [User-defined events](/eas/observe/events/).

Third-party packages can integrate with Expo Observe to report errors and events that help developers identify performance and usage issues. These are often problems that are difficult to detect from application code alone.

Reports should describe actionable issues that developers can fix. For example, a package might report:

- An image that is much larger than the device's screen
- A background task that takes too long to complete
- A native resource that loads slowly

A package integrates with the `expo-observe-interface` package, not with `expo-observe`. `expo-observe-interface` has no dependencies. When the app installs `expo-observe` and enables your integration with `Observe.configure()`, Expo Observe starts your integration and gives it a client that reports for it. When the app does not install `expo-observe`, your integration never starts.

## Prerequisites

<Prerequisites>
  <Requirement title="Expo SDK 58 and later">
    Third-party integrations require `expo-observe-interface`, and `expo-observe` version 58.1.0 and
    later in the app.
  </Requirement>
  <Requirement title="An app already using Expo Observe">
    Follow [Get started](/eas/observe/get-started/) to install `expo-observe` and create your first
    build.
  </Requirement>
</Prerequisites>

> **info** Third-party integrations work on iOS only for now. On Android, your integration does not start.

<Step label="1">

## Add `expo-observe-interface` as a dependency

Add `expo-observe-interface` to the `dependencies` of your package. Do not add `expo-observe`:

```json package.json
{
  "dependencies": {
    "expo-observe-interface": "^{{expoSdkVersion}}"
  }
}
```

</Step>

<Step label="2">

## Declare the integration configuration

Use declaration merging to add the key of your integration to `expo-observe-interface`. Use the npm package name of your package as the key:

```ts observe.types.ts
export type YourPackageIntegrationConfig = {
  thresholdMs?: number;
};

declare module 'expo-observe-interface' {
  interface ObserveIntegrationsConfig {
    'your-package'?: boolean | YourPackageIntegrationConfig;
  }
}
```

Export this declaration from your package entry point so TypeScript loads it when users import your package.

Developers using your package can then enable the integration with `Observe.configure()`:

```tsx app/_layout.tsx
import { Observe } from 'expo-observe';

Observe.configure({
  integrations: {
    'your-package': true,
  },
});
```

If the integration accepts options, developers can pass a configuration object instead of `true`:

```tsx app/_layout.tsx
Observe.configure({
  integrations: {
    'your-package': {
      thresholdMs: 1500,
    },
  },
});
```

The configuration is passed to your integration as JSON, so it cannot contain functions. Use data, such as lists of codes to skip, instead of callbacks.

</Step>

<Step label="3">

## Register the integration

Call `registerObserveIntegration()` once, when your package is imported. `setup` receives the configuration and a client, and returns a function that stops the integration:

```ts observe.ts
import { registerObserveIntegration } from 'expo-observe-interface';

import type { YourPackageIntegrationConfig } from './observe.types';

registerObserveIntegration<YourPackageIntegrationConfig>({
  name: 'your-package',
  setup({ config, observe }) {
    const thresholdMs = config.thresholdMs ?? 1000;
    const subscription = addOperationListener(operation => {
      if (operation.durationMs > thresholdMs) {
        observe.logEvent({
          name: 'your-package.expensive-operation',
          severity: 'warn',
          body: 'Reduce the work performed by this operation or increase the configured threshold.',
          attributes: { durationMs: operation.durationMs, thresholdMs },
        });
      }
    });
    return () => subscription.remove();
  },
});
```

Import the file from your package entry point:

```ts index.ts
import './observe';

export type { YourPackageIntegrationConfig } from './observe.types';
```

Expo Observe manages the lifecycle of the integration:

- `setup` runs when `Observe.configure()` enables the integration.
- When a later `Observe.configure()` call changes the configuration, the function that `setup` returned runs, and then `setup` runs again with the new configuration.
- When a later `Observe.configure()` call turns the integration off, only the function that `setup` returned runs.
- After the app reloads, `setup` runs again when `Observe.configure()` runs.

Errors that `setup` or the returned function throw are caught and printed as warnings.

</Step>

<Step label="4">

## Report errors, warnings, and events

The client that `setup` receives reports for your integration only. It has these functions:

- `observe.reportError()` records a non-fatal error. Errors appear in the **Errors** page. See [Error reporting](/eas/observe/errors/).
- `observe.reportWarning()` records a warning as an event with `warn` severity. The event has the message in its body and in the `message` attribute.
- `observe.logEvent()` records an event. See [User-defined events](/eas/observe/events/).

```ts observe.ts
observe.reportError({
  type: 'your-package.error',
  message: error.message,
  stacktrace: error.stack,
  code: error.code,
});
```

Use a lowercase name with the package name as the first segment for error types and event names. Separate segments with periods.

The client applies the same rules to every integration:

- A report with a `code` that is in the `ignoredCodes` option of your integration configuration is not recorded. If your reports have codes, add `ignoredCodes?: string[]` to your configuration type, so developers can set it.
- While the user has not granted consent to Observe, the client records nothing.
- After the function that `setup` returned runs, the client records nothing.

The client does not limit how often your integration reports. If your package can log the same message many times, for example once per frame, deduplicate the messages before you report them.

Each report function returns whether the client recorded the report.

</Step>

<Step label="5">

## Add a native integration

When your package detects issues in native code, report them from native code too. A native integration can start at launch, before your JavaScript code runs. It starts with the configuration of the last `Observe.configure()` call.

Add `ExpoObserveInterface` to the dependencies of your pod:

```ruby ios/YourPackage.podspec
s.dependency 'ExpoObserveInterface'
```

Implement `ObserveIntegration`:

```swift ios/YourPackageObserveIntegration.swift
import ExpoObserveInterface

final class YourPackageObserveIntegration: ObserveIntegration {
  let name = "your-package"

  func setup(config: [String: Any], observe: any ObserveClient) throws -> (() -> Void)? {
    let thresholdMs = config["thresholdMs"] as? Double ?? 1000
    let listener = OperationMonitor.shared.addListener { operation in
      if operation.durationMs > thresholdMs {
        observe.logEvent(
          ObserveEvent(
            name: "your-package.expensive-operation",
            body: "Reduce the work performed by this operation or increase the configured threshold.",
            attributes: ["durationMs": .number(operation.durationMs)],
            severity: .warn
          )
        )
      }
    }
    return { OperationMonitor.shared.removeListener(listener) }
  }
}
```

Register the integration once, as early as possible. For example, register it from an app delegate subscriber, and add the subscriber to `apple.appDelegateSubscribers` in the **expo-module.config.json** of your package:

```swift ios/YourPackageAppDelegateSubscriber.swift
import ExpoModulesCore
import ExpoObserveInterface

public class YourPackageAppDelegateSubscriber: ExpoAppDelegateSubscriber {
  public func subscriberDidRegister() {
    ObserveIntegrationRegistry.shared.register(YourPackageObserveIntegration())
  }
}
```

A native integration and a JavaScript integration with the same name get the same configuration.

</Step>

## Packages that use `Observe.registerIntegration()`

`Observe.registerIntegration()` calls its callback once, with the first configuration that enables the integration. It does not call the callback again when the configuration changes, and it cannot turn the integration off. To get the full lifecycle, move to `registerObserveIntegration()` from `expo-observe-interface`. This also removes the optional peer dependency on `expo-observe`.

Everything the [EAS Observe dashboard](/eas/observe/dashboard/) and the [`eas observe` commands](/eas/observe/eas-cli/) show is also available to an AI agent. Describe what you want to know in plain language, and the agent fetches the data, compares releases, and explains what it finds.

Three pieces give an agent access to your EAS Observe data. They work together, and you can use any one of them on its own:

- **Expo MCP Server** provides read-only tools that fetch metrics, routes, events, and session timelines from EAS. It works in any MCP client, including Claude on the web and mobile, where no terminal is available.
- **Expo Skills** teach the agent how EAS Observe works: which metrics exist, what their target values are, how to query them, and how to read the device and network params on a slow launch.
- **EAS CLI** gives an agent with terminal access the same data as tables or JSON. It is also the only way for an agent to query [errors](/eas/observe/errors/), which the Expo MCP Server does not expose yet.

| Approach        | Where it runs                                                      | What it provides                              |
| --------------- | ------------------------------------------------------------------ | --------------------------------------------- |
| Expo MCP Server | Claude, Claude Code, Codex, Cursor, VS Code, and other MCP clients | Live metrics, routes, events, and sessions    |
| Expo Skills     | Claude Code, Codex, Cursor, and other agents that read skills      | Setup, query, and interpretation knowledge    |
| EAS CLI         | Agents with terminal access                                        | Live data as tables or JSON, including errors |

## Set up your agent

<Step label="1">

Claude Code and Codex have an official Expo plugin that installs Expo Skills and registers the Expo MCP Server in one step. Other agents install the two separately.

<Step label="2">

### Give the agent the EAS CLI

This step applies to agents that can run terminal commands, such as Claude Code, Codex, and Cursor. Skip it for Claude on the web and mobile.

Install the EAS CLI and log in. The agent then runs the `eas observe` commands with `--json --non-interactive`, so the output is machine-readable and never waits for a prompt.

<Terminal
  cmd={{
    npm: ['$ npm install --global eas-cli', '', '$ eas login'],
    yarn: ['$ yarn global add eas-cli', '', '$ eas login'],
    pnpm: ['$ pnpm add --global eas-cli', '', '$ eas login'],
    bun: ['$ bun add --global eas-cli', '', '$ eas login'],
  }}
/>

</Step>

<Step label="3">

### Verify the setup

Open the agent in your project directory and ask:

```text Example prompt
Which versions of my app has EAS Observe seen in the last 7 days?
```

The agent either calls the `observe_versions` tool on the Expo MCP Server or runs `eas observe:versions --days 7`. Either way, it replies with the app versions, build numbers, and event counts from your project.

</Step>

## Point the agent at a project

Every Expo MCP Server tool for EAS Observe accepts a project ID or the full project name, such as `@owner/my-app`. When the agent runs inside your project directory, it reads the project ID from **app.json** under `extra.eas.projectId`. When it runs elsewhere, such as Claude on the web, name the project in your prompt.

The EAS CLI reads the project ID from the app config in the current directory. Outside the project directory, the agent passes `--project-id`.

## Example prompts

After setup, describe what you want to know. The agent picks the tool or command for you:

| Example prompt                                                         | What the agent does                                                         |
| ---------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| How does startup performance in 2.4.0 compare with 2.3.0 on iOS?       | Fetches metric summaries per version and compares median and p90 values     |
| Show me the 10 slowest time to interactive samples from the last week. | Fetches individual samples sorted slowest first, with their session IDs     |
| What happened during session `<session-id>`?                           | Fetches the session timeline, with every metric, event, and error           |
| Which screens take longest to become interactive?                      | Fetches navigation metrics per route and ranks them                         |
| Which custom events is the app logging, and how often?                 | Lists event names with their counts                                         |
| How long do over-the-air updates take to download in the field?        | Fetches the `update_download` metric summary                                |
| Which errors are most common in the latest release?                    | Runs `eas observe:errors` in the terminal, since the MCP has no errors tool |

## Workflows

### Investigate a slow launch

A slow launch is rarely explained by one number. The agent chains several queries and reads the context on each sample:

1. It fetches the metric summary to confirm which version and platform regressed.
2. It fetches the slowest time to interactive (TTI) samples for that version. Each sample carries [automatic params](/eas/observe/reference/metrics/#time-to-interactive-tti) that describe frame rate, device state, and network state during the launch.
3. It reads the params to classify the slowness. Many slow frames point to main-thread contention. A frozen frame points to a hard block, such as synchronous I/O. A high TTI with few slow frames points to a long but smooth launch sequence.
4. It checks whether the slow samples share a condition, such as low power mode, a cellular connection, or a slow first request.
5. It fetches one session timeline to see what else happened during that launch.

```text Example prompt
TTI on iOS got slower in 2.4.0. Find the slowest samples, tell me whether the
cause looks like code or conditions, and show me one session that explains it.
```

The `eas-observe` skill teaches the agent these diagnostic patterns, so install it even when the agent reads data through the Expo MCP Server.

### Compare two releases

Ask the agent to compare any two app versions, native builds, or EAS updates. It fetches summaries for both and reports the change per metric. Pass a short time range so the comparison reflects the current rollout:

```text Example prompt
Compare cold launch, warm launch, and TTI between build 142 and build 143 on
Android over the last 3 days. Flag any metric where p90 got worse by more than
10%.
```

### Analyze errors from the terminal

The Expo MCP Server does not expose error groups yet, so error analysis needs an agent with terminal access and the EAS CLI. The agent runs `eas observe:errors` for the grouped list, then `eas observe:errors --fingerprint <fingerprint>` for the stack traces of one group:

```text Example prompt
List the fatal errors from the last 7 days, then show me the stack trace of the
most common one and suggest where in the code it comes from.
```

See [`eas observe:errors`](/eas/observe/eas-cli/#eas-observeerrors) for the available filters.

### Start from the dashboard

The **Handoff to AI** button in the dashboard header copies the current page state as a structured prompt, including the filters you have applied. Paste it into an agent that has the Expo MCP Server, and the agent can fetch more data to answer follow-up questions. See [Handoff to AI](/eas/observe/dashboard/#handoff-to-ai).

## What the agent can access

Each Expo MCP Server tool maps to an EAS CLI command. All the tools are read-only. Timing values are in seconds, and results are paginated the same way as the CLI.

| Data                                    | Expo MCP Server tool      | EAS CLI command               |
| --------------------------------------- | ------------------------- | ----------------------------- |
| App versions, build numbers, update IDs | `observe_versions`        | `eas observe:versions`        |
| Aggregated statistics per app version   | `observe_metrics_summary` | `eas observe:metrics-summary` |
| Individual metric samples               | `observe_metrics`         | `eas observe:metrics`         |
| Navigation metrics grouped by route     | `observe_routes`          | `eas observe:routes`          |
| User-defined event names and counts     | `observe_event_names`     | `eas observe:events`          |
| Individual user-defined events          | `observe_events`          | `eas observe:events <name>`   |
| The full timeline of one session        | `observe_session`         | `eas observe:session`         |
| Errors grouped by fingerprint           | Not available             | `eas observe:errors`          |
| One metric, event, or error by ID       | Not available             | `eas observe:event`           |

The same plan limits apply as in the dashboard and CLI. When your plan does not include the data a tool asks for, the tool returns an upgrade message instead of data. See [Pricing](https://expo.dev/pricing) for what each plan includes.

## Data privacy

The Expo MCP Server returns your EAS Observe data to the agent you connect. From there, the agent and its model provider apply their own retention and training policies. EAS Observe data contains no personally identifiable information, but review those policies before connecting an agent to a project under regulatory requirements. See [Data privacy](/mcp/#data-privacy) for the full data flow.

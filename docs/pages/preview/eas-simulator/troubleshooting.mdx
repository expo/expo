<FAQ>

## Command not found

### `Command simulator:start not found`

The installed EAS CLI is too old. [Install or update EAS CLI](/eas/cli/), then inspect the command:

<Terminal cmd={['$ eas simulator:start --help']} />

The `simulator:*` commands appear in `eas --help` from EAS CLI 24.8.0. In earlier versions, the commands are hidden from the help output.

### `simulator:start` rejects a documented flag

Update to the latest version of [EAS CLI](/eas/cli/), then compare the command with the installed help:

<Terminal cmd={['$ eas simulator:start --help']} />

## Access and project errors

### EAS Simulator is not enabled for the account

Check before starting:

<Terminal cmd={['$ eas simulator:availability --json']} />

If `available` is `false`, do not retry `simulator:start`. Use a local simulator or emulator, or [join the waitlist](https://expo.dev/services/simulators) for access.

### EAS CLI reports that a user account is required

Log in interactively or provide `EXPO_TOKEN` in a headless environment:

<Terminal cmd={['$ eas whoami']} />

### EAS CLI reports that the project is not linked

Run the command inside the Expo project and initialize EAS:

<Terminal cmd={['$ eas init']} />

### `Device run session max duration must not exceed ... minutes for this account`

The requested `--max-duration-minutes` value is larger than the limit for your plan. The limit is 40 minutes on the Free plan and 115 minutes on paid plans. Any plan can set a custom value up to its limit. Use a smaller value, or omit the flag to use the plan maximum. See [How long an EAS Simulator session runs](/preview/eas-simulator/how-it-works/session-lifetime/).

## Session lifecycle problems

### The session takes a long time to start

Boot time varies with device capacity. While the device is starting, poll the existing session:

<Terminal cmd={['$ eas simulator:get --id <session-id> --json --non-interactive']} />

The session is ready when the status is `IN_PROGRESS` and `remoteConfig` is present. If it reaches `STOPPED` or `ERRORED`, or the start command reports a terminal failure, start a new session. Starting a second session while the first is still booting does not speed up the process.

### A non-interactive session did not stop automatically

`--non-interactive` returns after the controller is ready. It does not stop the session. Run:

<Terminal cmd={['$ eas simulator:stop']} />

### Starting a session left the previous session running

`simulator:start` creates a new session by default, even when **.env.eas-simulator** contains another session ID. It replaces the local configuration, but it does not stop the previous remote session.

List active sessions and stop the old one explicitly:

<Terminal
  cmd={['$ eas simulator:list --status in-progress', '$ eas simulator:stop --id <old-session-id>']}
/>

Use `--no-force` when you want `simulator:start` to fail instead of creating a new session while the environment already contains an ID. Give every session a descriptive `--name` so it is easy to identify in the list.

### The start command shows that the session is queued

The session waits for available concurrency on your account. Sessions use the same job concurrency as other EAS jobs, such as EAS Build. Queue time does not count toward the 15-minute startup timeout. Stop sessions that you do not need to free concurrency:

<Terminal cmd={['$ eas simulator:list --status new --status in-progress']} />

### A browser preview session stopped while someone used it

Controller activity from agent-device, Argent, or Appium resets the idle timer. Browser preview activity does not. For sessions that a person controls in the browser preview, omit `--max-idle-time-minutes` and use `--max-duration-minutes` to limit them.

## Controller and tunnel problems

### `Remote daemon is unavailable` or the tunnel endpoint is offline

The controller tunnel has dropped or the remote VM has ended. A dropped controller invalidates the installed app state, accessibility references, and connection configuration.

Stop the session if it is still active, then start a fresh session and repeat install → open → drive. Do not repeatedly retry a controller command against the dead endpoint.

### Screenshots show a local simulator instead of the remote device

If **.env.eas-simulator** has no connection details, agent-device can use a local simulator without an error. This can happen when another `simulator:start` command replaced the file. Confirm that `eas simulator:get --json` returns the session ID that the start command printed.

Run `eas simulator:exec npx agent-device@latest open <app>`. In a remote session, the **Session state** path starts with **/Users/expo/** on iOS or **/home/expo/** on Android. A path under your own home directory means that the agent controls a local device. See [How EAS CLI and agents select an EAS Simulator session](/preview/eas-simulator/how-it-works/agent-targeting/).

### `DEVICE_NOT_FOUND` when you select a second device

The agent-device `--device` flag accepts a device name only. To select a device by its UDID, use `--udid <UDID>` instead. To control a second device, also pass a separate `--session <name>`. See [Use a second device in the same session](/preview/eas-simulator/reference/devices/#use-a-second-device-in-the-same-session). List the device names:

<Terminal cmd={['$ eas simulator:exec npx agent-device@latest devices --platform ios']} />

### Argent returns `401 Unauthorized` after `argent link`

`argent link` without `--yes` keeps the old token when the URL is already linked. Link again with `--yes`:

<Terminal cmd={["$ argent link '<ARGENT_TOOLS_URL>' --token '<ARGENT_AUTH_TOKEN>' --yes"]} />

### A controller action hangs

Some iOS snapshots and interactions can take tens of seconds. If an action times out, refresh the interactive accessibility tree before retrying:

<Terminal cmd={['$ eas simulator:exec npx agent-device@latest snapshot -i']} />

The original action may have reached the device even when the response was delayed, and blindly retrying can perform it twice.

### `install requires an active session or an explicit device selector`

Pass the platform:

<Terminal
  cmd={[
    '$ eas simulator:exec npx agent-device@latest install com.example.app ./MyApp.app --platform ios',
  ]}
/>

### Screenshot reports that there is no active session

Open an installed app before taking the screenshot:

<Terminal
  cmd={[
    '$ eas simulator:exec npx agent-device@latest open com.example.app --platform ios',
    '$ eas simulator:exec npx agent-device@latest screenshot ./shot.png',
  ]}
/>

## App and build problems

### `Launch options require an application source`

`--launch-arg` and `--open-url` apply to an application installed during session startup. Pass exactly one source with the command:

- `--build-id <build-id>` for an EAS Build
- `--build-fingerprint <fingerprint-hash>` for the most recent finished EAS Build with that fingerprint
- `--application-archive-url <url>` for a remote application archive
- `--expo-go` for the Expo Go version matching the project SDK

For a local **.app** or APK, start a blank session and install it through agent-device or another controller instead.

### Expo Go cannot determine the SDK version

Run the command from an Expo project with a valid app config, or pass `--sdk-version <version>` together with `--expo-go`. The SDK override is valid only with `--expo-go`.

### The remote device does not contain the app

This is expected when the session starts without `--build-id`, `--build-fingerprint`, `--application-archive-url`, or `--expo-go`. Install a local simulator or emulator build through the controller, or start a new session with an application source.

### The screenshot shows old source code

A release build embeds JavaScript at build time. Rebuild it from the current source, confirm that an existing EAS Build has the matching fingerprint, or install a development build and connect it to Metro.

Changing source files does not update an already-installed release build.

### A recording did not download

The recording can still be a session artifact. Get the session with its ID and download the file from `artifacts[].downloadUrl`. See [Recover a recording that did not download](/preview/eas-simulator/how-to/capture-evidence/#recover-a-recording-that-did-not-download).

### Fast Refresh does not work

Confirm all of the following:

- The installed binary is a development build with `expo-dev-client`, not a release build
- Metro is running once, without another process occupying port 8081
- The development client is connected to the public Metro tunnel URL
- The simulator session and controller are still active

Use tunnel v2 in remote or headless agent environments:

<Terminal cmd={['$ EXPO_UNSTABLE_TUNNEL_V2=1 npx expo start --tunnel']} />

If the first connection fails, reset the simulator session and Metro once, then repeat the documented development-build flow. Reconnecting a release build cannot enable Fast Refresh.

## Browser preview problems

### The session page does not show the Android preview

Android sessions also include a browser preview that streams the emulator. The expo.dev session page does not show it inline yet; select **Open preview** to open it in a new tab. Android support is still in development, so some features that work on iOS may not work on Android yet. If the Android preview does not respond to input, control the emulator with agent-device, Argent, or Appium.

### The preview appears inside the simulator

The browser preview URL was opened as though it were an app URL. Open it in the desktop browser instead. It is a browser stream, not an application deep link.

## Network problems

### `--egress local is only supported with --platform ios`

Local egress uses the macOS system proxy, so it works only for iOS sessions.

### Local egress is not enabled for the account

Local egress is an experimental feature. Contact Expo to enable it for your account.

### Requests fail after the egress client disconnects

In a local egress session, proxied requests fail while the egress client is disconnected. The client tries to connect again. Keep `eas simulator:egress` running for the life of the session. The session keeps running and consuming usage while the client is disconnected.

### The app cannot reach a server on your computer through local egress

Local egress refuses local and private addresses unless you allow them. Start the session with `--egress-allow <host:port>` for each server, such as `--egress-allow localhost:3000`. See [Network traffic and local egress in EAS Simulator](/preview/eas-simulator/how-it-works/network-inspection/).

EAS Simulator and its CLI are experimental. Include the EAS CLI version, session ID, platform, controller type, and failing command when reporting a problem.

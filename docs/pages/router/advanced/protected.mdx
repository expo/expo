## Overview

Protected screens allow you to prevent users from accessing certain routes using client-side navigation. If a user navigates to a protected screen in a navigator that is already open, the navigation does nothing, or opens the [`redirectTo`](#redirect-to-a-specific-route) route when the screen has one. If a screen becomes protected while it is open, the stack replaces it with its `redirectTo` route, or removes it when it has none. If no screen remains, the stack opens the anchor route (usually the index screen) or the first available screen.

```tsx src/app/_layout.tsx
import { Stack } from 'expo-router';

const isLoggedIn = false;

export function AppLayout() {
  return (
    <Stack>
      <Stack.Protected guard={!isLoggedIn}>
        <Stack.Screen name="login" />
      </Stack.Protected>

      <Stack.Protected guard={isLoggedIn}>
        <Stack.Screen name="private" />
      </Stack.Protected>
      {/* Expo Router includes all routes by default. Adding Stack.Protected creates exceptions for these screens. */}
    </Stack>
  );
}
```

In this example, the `/private` route is inaccessible because the `guard` is false. When a user opens the app at `/private`, they are redirected to the anchor route, which is the **index** screen. When a user navigates to `/private` while its stack is mounted, the navigation does nothing.

Additionally, if the user is on `/private/page` and the `guard` condition changes to **false**, they will be redirected automatically.

When a screen's **guard** is changed from **true** to **false**, all of its history entries will be removed from the navigation history.

## Multiple protected screens

In Expo Router, a screen can **only exist in one active route group at a time**.

You should only declare a screen only once, in the most appropriate group or stack. If a screen's availability depends on logic, wrap it in a conditional group instead of duplicating the screen.

```tsx src/app/_layout.tsx
import { Stack } from 'expo-router';

const isLoggedIn = true;
const isAdmin = true;

export function AppLayout() {
  return (
    <Stack>
      <Stack.Protected guard={true}>
        <Stack.Screen name="profile" />
      </Stack.Protected>
      <Stack.Screen name="profile" /> // ❌ Not allowed: duplicate screen
    </Stack>
  );
}
```

## Nesting protected screens

Protected screens can be nested to define hierarchical access control logic.

```tsx src/app/_layout.tsx
import { Stack } from 'expo-router';

const isLoggedIn = true;
const isAdmin = true;

export function AppLayout() {
  return (
    <Stack>
      <Stack.Protected guard={isLoggedIn}>
        <Stack.Protected guard={isAdmin}>
          <Stack.Screen name="private" />
        </Stack.Protected>

        <Stack.Screen name="about" />
      </Stack.Protected>
    </Stack>
  );
}
```

In this case:

- `/private` is only protected if the user is logged in and is an admin.
- `/about` is protected to any logged-in user.

## Use the default redirect

When the app opens at a protected route without `redirectTo`, or when no screen remains after a guard change, the navigator opens its anchor route or the first available screen. If no route is accessible and no parent navigator has a fallback, the first screen stays and shows nothing.

## Redirect to a specific route

> **info** Available in **SDK 58 and later**.

Use the `redirectTo` prop when a protected route should redirect to a specific route. It accepts a string or object href, like [`Link`](/router/basics/navigation/#links-and-buttons), but only for routes of the app. An external URL in `redirectTo` throws an error. To send a user to an external URL, call [`Linking.openURL`](/versions/latest/sdk/linking/#linkingopenurlurl) from your app code.

```tsx src/app/_layout.tsx
import { Stack } from 'expo-router';

const isLoggedIn = false;

export function AppLayout() {
  return (
    <Stack>
      <Stack.Protected guard={isLoggedIn} redirectTo="/login">
        <Stack.Screen name="private" />
      </Stack.Protected>

      <Stack.Screen name="login" />
    </Stack>
  );
}
```

When a user navigates to a protected route with `redirectTo`, the router opens the `redirectTo` route instead. A push stays a push and a replace stays a replace. If the `redirectTo` route is also protected, the router follows its `redirectTo`. If a route in this chain is protected, has no `redirectTo`, and is in a navigator that is already open, the navigation does nothing. If the redirects form a loop or a chain of more than 20 redirects, the router throws an error.

When protected screens are nested, the outermost guard that fails decides the redirect. If that guard has no `redirectTo`, the router does not use the `redirectTo` of an inner guard. Navigation to the screen in a navigator that is already open does nothing, and a guard change removes the screen.

### When a guard changes

When a `guard` changes, each stack updates the screens that are already open. The stack does this before navigation that starts in the same function with `router` or `Link`:

- If the visible screen is blocked and has `redirectTo`, the stack replaces it with the `redirectTo` route. If the `redirectTo` chain ends at a protected route without `redirectTo`, the stack removes the screen instead.
- The stack removes all other blocked screens. These include a blocked screen below the top screen, the top screen in a tab that is not focused, a screen under a modal, and a preloaded screen.
- If no screens remain, the router uses the [default redirect](#use-the-default-redirect). If no route is accessible and no parent navigator has a fallback, the first screen stays and shows nothing.

The focused stack replaces the visible screen first, then removes the other blocked screens. A removed screen does not redirect later, for example, when its tab is focused again.

```tsx src/app/_layout.tsx
import { router, Stack } from 'expo-router';
import { useState } from 'react';

export default function RootLayout() {
  const [isLoggedIn, setIsLoggedIn] = useState(false);

  function signIn() {
    setIsLoggedIn(true);
    // Opens /home first, then pushes /profile on top of it.
    router.push('/profile');
  }

  return (
    <Stack>
      <Stack.Protected guard={!isLoggedIn} redirectTo="/home">
        <Stack.Screen name="login" />
      </Stack.Protected>
    </Stack>
  );
}
```

An `await` between the `guard` change and the navigation gives the same result.

> **tip** If a modal can change a guard, for example, with a sign-out button, put the modal in the protected group. In a stack with `(tabs)` and `account-modal`, where only `(tabs)` is protected, sign-out removes `(tabs)` and `account-modal` stays open.

## Tabs and Drawer

Protected routes are also available for [Tabs](/router/advanced/tabs/) and [Drawer](/router/advanced/drawer/) navigators.

```tsx src/app/_layout.tsx
import { Tabs } from 'expo-router/js-tabs';

const isLoggedIn = false;

export default function TabLayout() {
  return (
    <Tabs>
      <Tabs.Screen name="index" options={{ tabBarLabel: 'Home' }} />
      <Tabs.Protected guard={isLoggedIn}>
        <Tabs.Screen name="private" options={{ tabBarLabel: 'Private' }} />
        <Tabs.Screen name="profile" options={{ tabBarLabel: 'Profile' }} />
      </Tabs.Protected>

      <Tabs.Protected guard={!isLoggedIn}>
        <Tabs.Screen name="login" options={{ tabBarLabel: 'Login' }} />
      </Tabs.Protected>
    </Tabs>
  );
}
```

## Custom navigators

> **info** The stable custom navigator APIs are available in **SDK 58 and later**.

Navigators created with `createStandardRouterNavigator` or `integrateWithRouter` include a `.Protected` child. See [Custom navigators](/router/advanced/custom-navigators/) to create or integrate one.

## Static rendering considerations

Protected screens are evaluated on the client side only. During static site generation, no HTML files are created for protected routes. However, if users know the URLs of these routes, they can still request the corresponding HTML or JavaScript files directly. Protected screens are not a replacement for server-side authentication or access control.

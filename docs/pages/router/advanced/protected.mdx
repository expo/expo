## Overview

Protected screens allow you to prevent users from accessing certain routes using client-side navigation. If a user tries to navigate to a protected screen, the navigation does not happen. If a screen becomes protected while it is active, the user returns to the previous accessible screen. When no accessible screen remains, the navigator opens its anchor route (usually the index screen) or the first available screen.

```tsx src/app/_layout.tsx
import { Stack } from 'expo-router';

const isLoggedIn = false;

export function AppLayout() {
  return (
    <Stack>
      <Stack.Protected guard={!isLoggedIn}>
        <Stack.Screen name="login" />
      </Stack.Protected>

      <Stack.Protected guard={isLoggedIn}>
        <Stack.Screen name="private" />
      </Stack.Protected>
      {/* Expo Router includes all routes by default. Adding Stack.Protected creates exceptions for these screens. */}
    </Stack>
  );
}
```

In this example, the `/private` route is inaccessible because the `guard` is false. When a user attempts to navigate to `/private`, the current screen stays. A deep link to `/private` opens the anchor route, which is the **index** screen.

Additionally, if the user is on `/private/page` and the `guard` condition changes to **false**, the **private** screens are removed and the previous screen is shown again.

When a screen's **guard** is changed from **true** to **false**, all of its history entries will be removed from the navigation history. Screens that remain keep their state.

## Multiple protected screens

In Expo Router, a screen can **only exist in one active route group at a time**.

You should only declare a screen only once, in the most appropriate group or stack. If a screen's availability depends on logic, wrap it in a conditional group instead of duplicating the screen.

```tsx src/app/_layout.tsx
import { Stack } from 'expo-router';

const isLoggedIn = true;
const isAdmin = true;

export function AppLayout() {
  return (
    <Stack>
      <Stack.Protected guard={true}>
        <Stack.Screen name="profile" />
      </Stack.Protected>
      <Stack.Screen name="profile" /> // ❌ Not allowed: duplicate screen
    </Stack>
  );
}
```

## Nesting protected screens

Protected screens can be nested to define hierarchical access control logic.

```tsx src/app/_layout.tsx
import { Stack } from 'expo-router';

const isLoggedIn = true;
const isAdmin = true;

export function AppLayout() {
  return (
    <Stack>
      <Stack.Protected guard={isLoggedIn}>
        <Stack.Protected guard={isAdmin}>
          <Stack.Screen name="private" />
        </Stack.Protected>

        <Stack.Screen name="about" />
      </Stack.Protected>
    </Stack>
  );
}
```

In this case:

- `/private` is only protected if the user is logged in and is an admin.
- `/about` is protected to any logged-in user.

## What happens when access changes

The following rules apply when a guard is **false** and the screen has no `redirectTo`:

- A push, replace, or prefetch of the protected screen does nothing. The current screen and history stay the same.
- When the active screen becomes protected, the navigator removes it and shows the screen below it. It does not open another copy of the anchor route.
- When no accessible screen remains in the history, the navigator opens its anchor route once.
- When every screen of a navigator is protected, the navigator stays mounted, shows no screen, and logs a warning in development. When access returns, the navigator starts again at its anchor route.
- When guards in a parent layout and a child layout both fail, the parent guard decides. When nested `Protected` groups in one layout both fail, the outermost group decides.

> **warning** The router can check a guard only after its layout has rendered. Navigation into a layout that has not rendered yet opens that layout first. The guard then applies, but a replace has already removed the previous screen.

## Use the default redirect

If access is denied and no accessible screen remains, the navigator opens its anchor route or the first available screen.

```tsx src/app/_layout.tsx
import { Stack } from 'expo-router';

const isLoggedIn = false;

export function AppLayout() {
  return (
    <Stack>
      <Stack.Protected guard={isLoggedIn}>
        <Stack.Screen name="index" />
        <Stack.Screen name="private" />
      </Stack.Protected>

      <Stack.Screen name="login" />
    </Stack>
  );
}
```

In this example, the **index** screen is protected and the `guard` is **false**, so the router redirects to the first available screen: **login**.

## Redirect to a specific route

> **info** Available in **SDK 58 and later**.

Use the `redirectTo` prop when a protected route should redirect to a specific route. It accepts the same string or object href as [`Link`](/router/basics/navigation/#links-and-buttons).

```tsx src/app/_layout.tsx
import { Stack } from 'expo-router';

const isLoggedIn = false;

export function AppLayout() {
  return (
    <Stack>
      <Stack.Protected guard={isLoggedIn} redirectTo="/login">
        <Stack.Screen name="private" />
      </Stack.Protected>

      <Stack.Screen name="login" />
    </Stack>
  );
}
```

With `redirectTo`, a push or replace of the protected screen opens the redirect destination with the same action. When the active screen becomes protected, the navigator removes it and opens the destination as a new screen, even if the same route is already in the history. A relative `redirectTo`, such as `./upgrade`, resolves from the protected route.

If `redirectTo` points to another protected screen, the router follows that screen's `redirectTo`. If the redirects form a loop, the router throws an error.

If your code navigates in the same event handler that changes the guard, that navigation runs instead of the redirect.

## Tabs and Drawer

Protected routes are also available for [Tabs](/router/advanced/tabs/) and [Drawer](/router/advanced/drawer/) navigators.

```tsx src/app/_layout.tsx
import { Tabs } from 'expo-router/js-tabs';

const isLoggedIn = false;

export default function TabLayout() {
  return (
    <Tabs>
      <Tabs.Screen name="index" options={{ tabBarLabel: 'Home' }} />
      <Tabs.Protected guard={isLoggedIn}>
        <Tabs.Screen name="private" options={{ tabBarLabel: 'Private' }} />
        <Tabs.Screen name="profile" options={{ tabBarLabel: 'Profile' }} />
      </Tabs.Protected>

      <Tabs.Protected guard={!isLoggedIn}>
        <Tabs.Screen name="login" options={{ tabBarLabel: 'Login' }} />
      </Tabs.Protected>
    </Tabs>
  );
}
```

## Custom navigators

> **info** The stable custom navigator APIs are available in **SDK 58 and later**.

Navigators created with `createStandardRouterNavigator` or `integrateWithRouter` include a `.Protected` child. The navigator receives only the routes and descriptors of accessible screens. See [Custom navigators](/router/advanced/custom-navigators/) to create or integrate one.

## Static rendering considerations

Protected screens are evaluated on the client side only. During static site generation, no HTML files are created for protected routes. However, if users know the URLs of these routes, they can still request the corresponding HTML or JavaScript files directly. Protected screens are not a replacement for server-side authentication or access control.

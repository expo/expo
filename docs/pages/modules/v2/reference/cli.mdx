The `expo-modules` command has tools for modules that use Expo Modules API 2.0. It comes with the `expo` package, so a module that depends on `expo` doesn't need another dependency. Run it in the directory of the module:

<Terminal cmd={['$ npx expo-modules --help']} />

A command with a language prefix, such as `swift:expand`, uses the tools of that language and reads only its source files. A command without a prefix, such as `typegen`, gives a result that doesn't depend on the native language.

## Generate TypeScript types

`typegen` generates the TypeScript types of the native API that a module exports to JavaScript:

<Terminal cmd={['$ npx expo-modules typegen']} />

The command reads the Swift source files of the module: the `@ExpoModule`, `@SharedObject`, `@Record`, and `@Union` types, and the enums that implement `Enumerable`. It doesn't read Kotlin source files. It writes one file for the module, by default **src/native.types.ts**:

```ts src/native.types.ts
// @generated by expo-modules-cli. Edit only the doc comments by hand.
// Regenerate with `expo-modules typegen`.

import type { NativeModule, SharedObject } from 'expo';

export type Options = {
  quality?: number;
  name?: string | null;
  tags: string[];
};

export declare class Player extends SharedObject {
  constructor(url: string, options?: Options | null);
}

export declare class MyModule extends NativeModule {
  readonly version: string;
  greet(name: string, loudly?: boolean): string;
}
```

Import the generated types in the TypeScript code of the module, for example in the call to `requireNativeModule`. You can add doc comments (`/** ... */`) to the generated file. When you generate the file again, the command keeps each comment on the declaration with the same name, and shows a warning when it drops a comment.

A native type that has no TypeScript equivalent becomes `unknown`, and the command shows a warning. The command doesn't read the **node_modules**, **Pods**, **Tests**, **example**, and **examples** directories, and a few other directories for builds and tests.

| Option               | Description                                                                                                                |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| `[packageDir]`       | The directory of the module. Defaults to the current directory.                                                            |
| `-o`, `--out <path>` | The file to write, relative to the directory of the module. Defaults to **src/native.types.ts**.                           |
| `--check`            | Doesn't write the file. Exits with code 1 when the file is missing, out of date, or no longer necessary. Use it in CI.     |
| `--scanner <path>`   | The scanner executable to use. Defaults to the scanner of the `expo-modules-macros` version that `expo-modules-core` uses. |

The command replaces only a file that it generated. When the module exports nothing, it deletes the file.

> **info** The scanner that reads the source files is a macOS executable, so `typegen` runs only on macOS.

## Expand the Swift macros

`swift:expand` prints the code that the Swift macros generate, the same as **Expand Macro** in Xcode, without a build. It's useful to understand an error that points into the generated code.

<Terminal
  cmd={[
    '$ npx expo-modules swift:expand ios/MyModule.swift',
    '# Only one member',
    '$ npx expo-modules swift:expand --symbol MyModule.greet ios/MyModule.swift',
  ]}
/>

The command prints the expanded source code, and prints the errors and warnings of the macros in the `<file>:<line>:<column>: error: <message>` format. It exits with code 1 when there is an error. For a directory, it expands only the files that use a macro.

With `--symbol`, a type prints the expanded type and the extensions that its macros add, and a member prints its type with only that member.

The output can differ from a build in a few details, for example the unique names of generated declarations. Errors of the type checker still need a build.

## Check the Swift macros

`swift:check` prints only the errors and warnings of the macros and a summary, without a build. It exits with code 1 when there is an error, so you can use it in CI. Without a path, it checks the current directory.

<Terminal
  cmd={[
    '$ npx expo-modules swift:check',
    '$ npx expo-modules swift:check --symbol MyModule.greet ios',
  ]}
/>

`swift:expand` and `swift:check` have the same options:

| Option             | Description                                                                                                                       |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------- |
| `--symbol <name>`  | Only one type (`MyModule`, `MyModule.Options`) or member (`MyModule.greet`), and only its errors and warnings. You can repeat it. |
| `--json`           | Prints a JSON report. The exit code is 0 even when there are errors.                                                              |
| `--scanner <path>` | The executable to use. Defaults to the one of the `expo-modules-macros` version that `expo-modules-core` uses.                    |

Both commands need `expo-modules-macros` 0.27.0 or later.

## Mocks

The mock generator of [Mocking native calls](/modules/mocking/) reads only modules that use the module definition DSL (domain-specific language). It doesn't generate mocks for `@JS` members.

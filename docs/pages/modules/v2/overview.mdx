Expo Modules API 2.0 is a new way to write the native side of an Expo module. You write plain Kotlin and Swift declarations and mark the ones that JavaScript can use. A compiler plugin generates the code that binds them to JavaScript.

> **warning** Expo Modules API 2.0 is in beta, and its API can still change.

> **info** Expo Modules API 2.0 is available in **SDK 58 and later**.

## How it works

The following module exports a function, an asynchronous function, and an event:

<CodeBlocksTable tabs={['MyModule.kt', 'MyModule.swift']}>

```kotlin
import io.github.expo.modules.v2.Event
import io.github.expo.modules.v2.ExpoModule
import io.github.expo.modules.v2.JS
import io.github.expo.modules.v2.Module
import io.github.expo.modules.v2.Record

@Record
data class ProgressEvent(val percent: Double)

@ExpoModule
class MyModule : Module() {
  @JS
  fun greet(name: String): String = "Hi, $name"

  @JS
  suspend fun downloadAsync(url: String) {
    // ...
  }

  @Event(name = "progress")
  private val onProgress = event<ProgressEvent>()
}
```

```swift
import ExpoModulesCore

@Record
struct ProgressEvent {
  var percent: Double
}

@ExpoModule
public final class MyModule: Module {
  @JS
  func greet(name: String) -> String {
    "Hi, \(name)"
  }

  @JS
  func downloadAsync(url: String) async throws {
    // ...
  }

  @Event
  var onProgress: (ProgressEvent) -> Void
}
```

</CodeBlocksTable>

JavaScript loads the module by its name, the same as a module that uses the [module definition DSL](/modules/module-api/) (domain-specific language):

```ts
import { requireNativeModule } from 'expo';

const MyModule = requireNativeModule('MyModule');

MyModule.greet('Expo'); // "Hi, Expo"
```

The annotations in Kotlin and the macros in Swift have the same names:

- `@ExpoModule` turns a class into a module. The module name defaults to the class name.
- `@JS` exports a function or a property to JavaScript. A `suspend` function in Kotlin or an `async` function in Swift returns a promise in JavaScript.
- `@Event` declares an event that the module sends to JavaScript.
- `@Record` declares a type that converts to and from a JavaScript object.

## Differences from the module definition DSL

The [module definition DSL](/modules/module-api/) describes a module at runtime, in the `definition()` function. Expo Modules API 2.0 reads your declarations at compile time instead. This has the following effects:

- **No definition function.** The declarations of the class are the module. You don't repeat the name and the types of each function in a DSL component, such as `Function` or `AsyncFunction`.
- **Errors at build time.** In Swift, the macros check that each argument type can convert from a JavaScript value and each return type can convert to one. A type that can't convert is a build error, not a runtime error. Types that use `Any` convert at runtime instead.
- **Less overhead per call.** In Swift, the generated code decodes the arguments, calls the function, and encodes the result directly, without a dynamic path for each call.
- **Records without field wrappers.** In Kotlin, each `val` or `var` parameter of the primary constructor is a field. In Swift, each stored property is a field, except `static`, `private`, `fileprivate`, and `lazy` properties. You don't mark each field with `@Field`.

## Language support

Expo Modules API 2.0 is available in Kotlin and Swift. Kotlin doesn't support all the features of Swift yet. Each section of these docs shows the languages that support its feature. For the full list, see [Feature support](/modules/v2/feature-support/).
